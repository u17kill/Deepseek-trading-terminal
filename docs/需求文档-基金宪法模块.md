## 0. 一页速览

这份文档只有一件事要说清楚：**这一页是全终端唯一一页「用户写的东西比代码更重要」的页面。**
其余十四页丢了正文，重跑脚本或重写一次判断就行；这一页丢了，就是几个月的思考没了，而且
**不会有任何报错**——页面照常显示一份看起来很完整的文稿，用户要过很久才发现不对。

所以下面六条不是「最佳实践」，是这一页能存在的前提。每条都写了违反之后的**具体后果**。

| # | 约束 | 违反之后会发生什么 |
|---|---|---|
| **1** | 正文存 `data/charter/fund-charter.json`，**在构建产物之外** | 正文若住在 `output/*.html` 里，一次 `build_dashboard.py` 就把它还原成种子。用户当天不会发现，第二天打开发现「我上周加的第十一条没了」，而且以为是浏览器的问题 |
| **2** | 种子只在**保存文件不存在**时读一次 | 种子若在每次启动/构建时都比对或补齐，用户删掉的信条会自己长回来，用户改过的标题会自己改回去 |
| **3** | **读取失败 ≠ 没有文件**，不许静默退回种子 | 退回种子是这个模块最坏的一种「善意」：用户看到一份完整文稿，以为修改丢了，于是**在这份种子页面上继续编辑、再保存**，把真文件彻底覆盖。丢失变成不可逆 |
| **4** | 保存必须带 `revision`，不一致返回 409，**由用户裁决** | 两个标签页各改一半，谁后写谁赢，另一边的改动静默消失。自动合并正文是本项目少数几个「猜错就没法回头」的动作 |
| **5** | 写之前备份、临时文件 + `os.replace` 原子替换 | 写完再备份，备份的就是已改坏的那一版。直接覆盖写，进程在写到一半被杀，得到半份 JSON——而半份 JSON 会让第 3 条被执行，于是连备份都可能被当成「没有文件」 |
| **6** | 页面**不补全、不润色、不自动编号改写正文** | 这一页的价值在于「我当初是这么想的」。程序改一个字，用户就再也分不清哪句是自己的 |

第 1 条与 `.gitignore` 有关，容易被当成疏漏：**`data/charter/` 默认不入库是特意设计的**，
不是忘了放行。正文在源码之外，`git pull` / `git checkout` 才碰不到它。代价见 §11。

## 1. 定位

### 1.1 它回答什么问题

终端十五个页签回答的都是「市场怎么样」「我在哪」，基金宪法回答的是**「我为什么这么做」**。
它是那些问题的前提：一份可以随时翻回去重读、并且由用户自己维护的长期原则。

这个定位决定了三件事：

1. **层级高于普通页签。** 它不是一个被查看的视图，是一份被遵守的约束。所以入口不在菜单里（§3.1）。
2. **只能是「一份」。** 不是多文件知识库，不是笔记的第二份。多份宪法会立刻产生「现在该看哪份」的问题。
3. **正文必须能改。** 一份写死在代码里的原则等于一段文案。用户改了想法，页面就得跟着改，
   而且改完必须在下一次构建、下一次重启、下一次 `git pull` 之后**仍然是改后的版本**。

### 1.2 它不是

- 不是 AI 摘要页：不总结、不提炼要点、不生成「一句话版本」。
- 不是交易信号：正文里出现的 3% / 25% 这类数字是用户自己的风险上限，程序**不读取、不校验、
  不据此限制任何下单**（本终端本来也没有下单功能）。
- 不是多人协作：没有作者、没有审批、没有评论。
- 不是跨设备同步：两个地址各存各的（§11 Q1）。

## 2. 范围

### 2.1 本期包含

1. 页头右上角常驻入口（盾牌 + 勾，浅蓝底蓝字，当前页深蓝底白字）。
2. 站内独立页 `#charter`：面包屑 + 眉题 + 标题/副标题 + 工具条 + 状态条 + 提示条 +
   可折叠「本机草稿与恢复」+ 总纲卡 + 目录/正文双栏 + 末尾深蓝「最终准则」块。
3. 阅读态全文展开：支柱序号 + 中文名 + 英文名；信条卡片（全局编号 / 标题 / 多段正文 /
   可选要点 / 可选要点后补充 / 突出总结）。
4. 编辑态：改标题、副标题、总纲、最终准则标题与全文；支柱增删改名排序；信条增删改、
   跨支柱移动、同支柱内排序。
5. 右侧抽屉表单：应用 / 取消 / 导出当前草稿；Tab 焦点循环；Esc 取消；关闭后焦点回原位。
6. 三层数据：构建期快照 → `GET /api/charter` → `localStorage` 草稿。
7. `PUT /api/charter`：revision 版本号、409 冲突、备份 30 份、临时文件 + 原子替换。
8. 冲突裁决界面：使用文件内容 / 用本页覆盖文件 / 导出本页。
9. 导入导出 JSON（导入先作为草稿、需确认；导出在抽屉有未应用输入时带 `form`）。
10. 八态状态条 + 本机草稿与恢复（含跨标签页的其它草稿、手动恢复、删除）。
11. 独立页的路由支持：`PANE_HASH` 登记、`applyPane` 的 standalone 分支、入口按钮选中态。

### 2.2 本期不做（及理由）

| 不做 | 理由 |
|---|---|
| 多份宪法 / 版本分支 | 会产生「现在该看哪份」的歧义。要留旧版，导出 JSON 或看 `backups/` |
| 服务端自动合并正文 | 合并算法猜错一次就没法回头。宁可 409 让人选 |
| 富文本 / Markdown 渲染 | 正文是纯文本。渲染会让人以为 `*` 是加粗，而不是自己写的星号 |
| 全文检索 / 跨页引用 | 一份宪法几千字，浏览器自带 Ctrl+F 就够 |
| 自动编号写进正文 | 编号是排版（§4.2），写进正文后每插入一条都要改十条 |
| 把 3% / 25% 变成风控规则 | 那是用户的判断，不是程序的输入。程序认数字，就会在用户改措辞时误判 |
| AI 改写 / 生成信条 | 这一页的内容由人写，红线 21 与红线 14 都指向同一件事 |
| 跨设备同步 | 需要共同服务端 + 权限模型 + 冲突策略，不在本期（源需求文档 §7 也明确不要求） |

## 3. 页面结构

### 3.1 入口：页头最右上角

位置是**硬要求**（源需求文档 §2：不放到左侧栏作为普通菜单）。本仓库实现为页头 `.upd`
容器内的**第一项**：

```html
<a class="ct-entry" id="ctEntry" href="#charter"
   title="基金宪法 · 长期投资原则（Ctrl/⌘ 点击新开）">
  <svg viewBox="0 0 24 24" ...>盾牌 + 勾</svg>
  <span>基金宪法</span>
</a>
```

| 项 | 值 | 说明 |
|---|---|---|
| 位置 | `.upd` 内第一位 | 实测 1440 宽下 `x:1180, y:16`，尺寸 90×32 |
| 常态 | 底 `#eef5fe` / 字 `#1f6feb` / 边框细 | 与「更新数据」等普通操作按钮视觉区分 |
| 当前页 | 底 `#1f6feb` / 字与图标 `#fff` | `.ct-entry.on`，由 `applyPane` 切换 |
| 图标 | 14×14 线性盾牌 + 勾，`stroke-width:1.7` | 不用填充版：填充在 12px 字号旁会显得重 |
| 行为 | `href="#charter"`，站内跳转 | **不新开标签页**；Ctrl/⌘ 点击才新开（浏览器默认行为，`title` 里写明） |

### 3.2 路由：一张独立页，不进菜单

它是一张 **standalone pane**：`pane15` 在 DOM 里存在，但没有任何 `data-p` 按钮指向它。

```js
// applyPane(p)
let cur = btns.find(b => b.dataset.p === p);
const standalone = !cur && !!document.getElementById("pane" + p);
if (!cur && !standalone) cur = btns[0];   // 认不出才兜底回第一页
```

三处必须同时成立，少一处就退化成「点了没反应」或「被弹回首页」：

1. `<section id="pane15">` 存在于 DOM；
2. `PANE_HASH` 里有 `"#charter": "15"`——**不进菜单不等于不进映射表**，否则地址栏写不进、没法收藏；
3. `applyPane` 的 standalone 分支。

不进菜单的直接后果：右侧菜单不会被点亮（`tabOn: 0`）。「你在哪一页」由入口按钮的
`.on` 状态承担，副产物是它同时也成了「点一下能回来」的按钮。

**但「不点亮」不等于「不设显隐」。** 第二层页签的可见性是 `applyPane` 按组设的，而 HTML
里 15 个按钮默认全部可见——首屏直接打开 `#charter` 时如果只清 `on` 不设 `display`，
页签栏会露出一整排 15 个、把 1132px 撑满。所以 standalone 分支多一步：若一个按钮都还没被
过滤过，就按第一组收敛一次（第一层同步点亮该组）。从首页点进来时这条不触发，
**它只影响「收藏了 `#charter` 直接打开」这一种进入方式**——也正因如此，最容易漏。

| 项 | 1440 | 390 |
|---|---|---|
| 横向溢出 | `0` | `0` |

- **`#pane15 [hidden]{display:none !important}`。** 「本机草稿与恢复」的容器被设成

## 4. 功能需求

### FR-1 阅读态：全文展开，不摘、不折、不分页

- 十条信条**全部**渲染，正文段全出，不出现「展开更多」。
- 不用轮播、不用一条一页、不用手风琴。
- 支柱头显示序号（`01`…）+ 中文名 + 英文名；英文名可空。
- 信条卡片显示全局编号（`01`…`10`，跨支柱连续）+ 标题 + 段落 + 可选要点 + 可选补充 + 总结。
- 最终准则块在正文之后、页面底部，**始终显示**（不可折叠）。

### FR-2 目录与滚动

- 目录逐条列出支柱（序号 + 中文名），点击平滑滚动到对应支柱。
- 滚动时自动点亮当前支柱（`ctScrollSpy`）。
- 目录少于 2 条支柱时不显示目录栏（单栏，正文占满）。

### FR-3 标题自动生成

- `doc.title` 非空 → 用它。
- 为空 → 按条数生成：**恰好 10 条**显示「投资十大信条」，**其它条数**显示「投资信条」。
- 这条规则的意义：删掉一条之后标题会自己变成「投资信条」，不会出现「十大信条」下面
  只有九条的笑话。用户想要固定标题就自己填。

### FR-4 编号是排版，不是数据

- 支柱编号 `01` 起，信条编号跨全部支柱连续 `01` 起。
- **新增 / 删除 / 上移 / 下移 / 跨支柱移动之后自动重排**，编号永远等于「当前顺序」。
- id 与编号**完全解耦**：改标题、改顺序都不改 id（§6.1）。目录定位、抽屉指向、
  恢复副本的锚点全用 id。

### FR-5 编辑态：先草稿，再保存

- 点「编辑基金宪法」进入管理态：按钮变「预览」（可切回干净阅读视图，**不丢改动**）、
  露出结构操作、卡片上出现工具。
- 两个动作必须分开：**「应用到页面」**只把抽屉内容合进页面草稿；
  **「保存全部修改」**才写文件。把两者合成一个按钮，等于每改一段就落一次盘。
- 切换编辑/预览不影响脏标记；预览态下若有未保存修改，状态条仍显示「有未保存修改」。

### FR-6 支柱操作

| 操作 | 规则 |
|---|---|
| 新增 | 中文名必填，英文名可选；排在末尾；新增后若为空显示「这个支柱还没有信条」引导 |
| 改名 | 抽屉内改，应用后生效 |
| 上移/下移 | 首条禁用「上移」、末条禁用「下移」；移动后全文重排编号 |
| 删除 | 必须确认，且提示**会一起删掉几条信条**（`其中 2 条信条会一起删除`） |
| 空支柱 | 允许存在（用户可能先搭骨架） |

### FR-7 信条操作

| 操作 | 规则 |
|---|---|
| 新增 | 全局工具条或支柱内均可；默认落到当前支柱末尾 |
| 字段 | 所属支柱 / 标题 / 正文段 / 要点 / 要点后补充 / 总结 |
| 必填 | 标题必填、所属支柱必须存在；**正文可全空**（用户可能只记一个标题） |
| 跨支柱移动 | 抽屉里改「所属支柱」→ 追加到目标支柱**末尾**；同支柱内编辑保持原位置 |
| 排序 | 同支柱内上移/下移 |
| 删除 | 单独确认 |

### FR-8 抽屉表单

- 右侧 560px 抽屉，遮罩，字段说明明写「段落间空一行」「要点每行一条」。
- **「应用到页面」前先校验**：失败在表单内提示（`#ctFormErr`），**不清空输入**。
- 应用后：更新页面草稿、关闭抽屉、**不写文件**。
- 取消时若文字已改，需确认。
- Esc 取消；Tab / Shift+Tab 焦点在抽屉内循环；关闭后焦点回到触发元素。
- 抽屉打开时焦点落在标题输入框（实测 `focus: ctKTitle`）。

### FR-9 结构操作的回退能力

- 每一次结构变更都同时更新页面草稿与 `localStorage` 草稿（防抖）。
- 「重读文件」是**显式出口**：确认后丢弃页面草稿、重新读盘。
- 「本机草稿与恢复」里能看到本页与其它页的草稿，可单条恢复或删除。

## 5. 数据流

### 5.1 三层

| 层 | 位置 | 何时读 | 何时写 | 丢了会怎样 |
|---|---|---|---|---|
| L1 构建期快照 | HTML 内 `/*__CHARTER__*/` | 页面打开那一刻 | 构建时 | 无（构建必带） |
| L2 接口实时 | `GET /api/charter` | `ctInit()` 一次；保存 / 重读后 | — | 停在 L1 上，状态条标「读取失败」 |
| L3 本机草稿 | `localStorage: ct.draft.<tabId>` | `ctInit()` 在 `ctClaimTab()` 之后 | 每次输入防抖 | 关页面即丢未保存修改 |

优先级：**L2 > L1**（能读盘就以盘为准，快照只保证离线可读）；**L3 不是数据源，是提示源**
——它只在「与 L2 不同」时才提示恢复。

### 5.2 装载路径必须统一走 `ctAdopt`

四条装载路径：`ctInit` / 保存成功 / 重读 / 使用文件内容。四条都必须经过同一个归一函数
`ctAdopt(doc, meta)`，并同时刷新 `ctFile`（文件的归一版）与 `ct.document`（页面的归一版）。

**踩过的坑**：种子缺 `bullets` / `afterBullets` 字段，`ctFrom` 会补成空数组/空串，
而 `ctFile` 存的是未归一的原始 JSON。两者深度比较永远不相等，于是页面一打开就显示
「有未保存修改」、保存按钮常亮。修法不是补种子字段，而是**所有装载都做双重归一**，
脏判定统一由 `ctDirty()` / `ctCanSave()` 走归一后的值。

### 5.3 草稿与标签页

草稿键是 `ct.draft.<tabId>`，`tabId` 存 `sessionStorage`。问题在于**浏览器「复制标签页」会把
`sessionStorage` 一起复制**——两个标签页于是写同一个键，A 打字、B 打字，互相覆盖。

解法：

```js
// ctClaimTab()：开一个 BroadcastChannel 问一声
// 广播 {ask: sid}；若收到 {taken: sid}，说明已有页面在用这个 id → 换新 id
const chan = new BroadcastChannel("ct.tab");
```

`ctInit` 里 `await ctClaimTab()` 之后才读草稿。没有 `BroadcastChannel` 的环境直接返回，
退化为「可能撞键」，但不报错。

### 5.4 八种状态

| kind | 徽标 | 文案 | 触发 |
|---|---|---|---|
| `init` | 中性 | 初始文稿 · 尚未写入文件 | 文件不存在，读的是种子 |
| `saved` | 中性 | 已保存 · YYYY-MM-DD HH:MM | 保存成功后，时间取服务端 `updatedAt` |
| `unsaved` | 警示 | 有未保存修改 · 草稿已保留 | 页面草稿 ≠ 文件 |
| `nostore` | 错误 | 草稿未保留 · 改动只在当前页 | `localStorage` 写入抛错 |
| `saving` | 警示 | 正在保存… | PUT 在飞 |
| `failed` | 错误 | 保存失败 · <原因> | 网络 / 500 / 413 |
| `conflict` | 错误 | 版本冲突 · 文件已被其他页面修改 | 409 |
| `loadfail` | 错误 | 读取失败 · <原因> | GET 500 / 网络断 |

**不许「点了按钮就显示已保存」**——`saved` 只在响应体带 `revision` 与 `updatedAt` 时置位。

### 5.5 两条「不丢字」的路径

1. **抽屉里未应用的文字。** 它不属于 `document`，只存在于表单。草稿里因此存两个字段：
   `dDoc`（整份文档）与 `dForm`（`{mode, pillarId, principleId, values}`）。刷新后
   **两个条件分别判断**：`dDoc` 与文件不同 → 恢复文档草稿；`dForm` 非空 → 恢复表单并
   **重新打开抽屉**，提示语与前者分开写（否则用户以为那半截已经在正文里了）。
2. **导入的未应用输入。** 导出的 JSON 在抽屉有输入时带 `form` 字段；导入时若带 `form`，
   载入文档后把抽屉按「导入的未应用输入」重新打开。

## 6. 数据契约

### 6.1 文档结构

```ts
type Principle = {
  id: string;              // 稳定唯一，ASCII 字母数字 / _ / -
  title: string;           // 必填，≤300
  paragraphs: string[];    // ≤100 段，每段 ≤20000
  bullets?: string[];      // 可选，≤100 条
  afterBullets?: string;   // 可选补充
  conclusion: string;      // 总结，可空
};
type Pillar = {
  id: string;
  name: string;            // 必填，≤60（目录里横排，太长会挤走别的行）
  english: string;         // ≤120，可空
  principles: Principle[];
};
type CharterDocument = {
  schemaVersion: 1;
  title: string;           // "" = 自动标题
  subtitle: string;
  manifesto: string;       // 总纲
  pillars: Pillar[];       // ≤50
  finalTitle: string;
  finalParagraphs: string[];  // ≤100 段
};
```

**未知字段必须原样保留。** `normalize()` 固定键序、补默认值，但不删它不认识的键——
将来加了字段的文稿在旧版本上打开一次、保存一次，字段不能消失。

### 6.2 上限（服务端与浏览器两侧都校验）

| 常量 | 值 | 为什么是这个数 |
|---|---|---|
| `MAX_PILLARS` | 50 | 目录是 198px 单列，超过 50 条已经不是「四大支柱」了 |
| `MAX_PRINCIPLES` | 500 | 总量上限，防止误粘贴整本书 |
| `MAX_TITLE` | 200 | 页面标题 |
| `MAX_PILLAR_NAME` | 60 | 目录一行能放下 |
| `MAX_PILLAR_EN` | 120 | 眉题位置的长英文名 |
| `MAX_PTITLE` | 300 | 信条标题 |
| `MAX_PARAGRAPH` | 20000 | 单段；超过说明用户粘错了东西 |
| `MAX_PARAGRAPHS` | 100 | 每条信条最多 100 段 / 要点最多 100 条 |
| `MAX_FILE` | 1 MB | 请求体与文件双向上限 |
| `RESERVED_ID` | `final-principle` | 最终准则的锚点，**不许**被某条信条占用 |

### 6.3 校验分两档

| 档 | 在哪 | 做什么 |
|---|---|---|
| 宽松（浏览器） | `ctClientValidate` | 结构、必填、id 唯一且合法、上限。**提前拦**，给逐条错误 |
| 严格（服务端） | `charter.validate` | 同上，且是**唯一权威**。浏览器能绕，服务端不能 |

两档的规则必须一致——不一致就会出「页面说可以，保存被拒」。所以两边共用同一份常量语义，
错误文案也保持一致的前缀：`数据校验失败：<具体原因>`。

### 6.4 id 只认 ASCII

```python
# 只认 ASCII 字母数字：str.isalnum() 对中文也返回 True，会把「生存」放进来
if not ((ch.isascii() and ch.isalnum()) or ch in "_-"):
    return False
```

这不是洁癖：id 会出现在 `data-id`、锚点、以及将来可能的 URL 里。中文 id 不报错，
只会在某天变成一堆 `%E7%94%9F%E5%AD%98`，而且复制粘贴时看不出来。

### 6.5 revision

`revision = sha256(规范化 JSON)`，完整 64 位十六进制；`charter.py` 自检时只印前 12 位
（`064eb93aec04`），接口与文件里都是完整值。规范化 = `sort_keys=True` + 紧凑分隔符（`,` `:`）。

**不是文件字节哈希。** 换个编辑器保存一次、缩进从 2 格变 4 格、键序变了，
文件字节完全不同但**内容一模一样**——按字节算就会误判成「别人改过」，每次都弹冲突。
反过来，只要内容真变了，语义哈希一定不同。这才是「版本」该有的意思。

### 6.6 写回五步

```
save(doc, base_revision):
  ① validate(doc)                    → 失败 400，不落盘
  ② load() 取当前 revision            → 不等 409，带回 document/revision/updatedAt
  ③ 旧文件 → backups/fund-charter-<ts>.json，滚动保留 30 份
  ④ 写临时文件（同目录，保证同文件系统）
  ⑤ os.replace 原子替换
```

任一步失败都不留半份文件。目录不存在时先建（`os.makedirs(exist_ok=True)`）。

### 6.7 备份

- 位置：`data/charter/backups/`，与正文同盘同目录树，**不在构建产物里**。
- 命名：`fund-charter-YYYYMMDD-HHMMSS.json`。
- 保留：滚动 30 份，超出删最旧。
- 接口返回最后一次备份的文件名（`backup`），让用户知道「这次写之前存了一份」。
- **首次保存没有备份**（还没有旧文件可备），`backup` 为空串——这是正常值，不是失败。

## 7. 接口契约

### 7.1 `GET /api/charter`

```
200 { ok, document, revision, updatedAt, source, path, backups }
```

| 字段 | 含义 |
|---|---|
| `source` | `"file"` 或 `"seed"`。**这个字段是给用户看的**，页面据此决定状态条显示 `init` 还是 `saved` |
| `path` | 实际读取的文件绝对路径（排障用；本机工具，不涉及隐私外泄） |
| `backups` | 备份份数与最近一份的文件名 |
| `Cache-Control` | `no-store`——每次现读盘 |

失败：`500`（读不了 / 解析不了），**不许**返回 `source:"seed"` 掩盖。

### 7.2 `PUT /api/charter`

```
请求  { document, revision }
200   { ok, revision, updatedAt, bytes, backup, path, document }
```

| 码 | 含义 | 页面动作 |
|---|---|---|
| `400` | 非 JSON / 没有 `document` / 校验失败 | 表单内逐条报错，**保留输入** |
| `403` | 跨站 Origin | 明说「拒绝跨站保存」 |
| `409` | revision 不一致 | 进入冲突态，三个按钮（§7.4） |
| `413` | 请求体 > 1 MB | 提示「文稿过大」，建议导出后精简 |
| `429` | 正在保存 | 提示稍后重试；**不是**冲突 |
| `500` | 写盘失败 / 文件损坏 | 保留编辑，允许重试 / 导出 |

### 7.3 三处必须写对的实现细节

1. **`_origin_ok()` 用白名单集合，不用监听地址。** 拿 `server_address` 当基准会把正常保存
   判成跨站（某些环境把 `127.0.0.1` 规范成 `localhost`）。现在允许
   `127.0.0.1` / `localhost` / `::1` 任一配本机端口；`Origin` 为空放行（curl、`file://`）。
2. **`_read_body(limit)` 超限时先把请求体读完，再抛 413。** HTTP/1.1 keep-alive 下不读完
   就回包，**下一条请求**会从头错位——表现为「保存超限之后所有请求开始串味」，
   而报错完全指不到这里。
3. **`_ct_lock` 只锁写。** 读每次现读盘（多标签页要看得到别人的修改），写串行化；
   忙时返回 429 而不是排队——让第二个标签页立刻知道「不是我慢，是有人在写」。

### 7.4 冲突裁决界面

409 之后不能只有一个「重试」。三个动作：

| 按钮 | 做什么 | 保护 |
|---|---|---|
| 使用文件内容 | 载入服务端那份 | **先把本页另存成恢复副本**；存不下（`localStorage` 满）就**不许丢**，改提示「请先导出」并给导出按钮 |
| 用本页覆盖文件 | 以服务端的 `revision` 为基版本重新保存 | 先 `confirm` 写明「会备份磁盘这一版」「另一页的修改会被替换」；保存时服务端**再校验一次**最新 revision |
| 导出本页 | 存一份 JSON 到本地 | 永远可用 |

## 8. 内容与纪律

1. **正文一字不改。** 不做拼写检查、不做全角半角转换、不把 `"` 变成 `“”`、不合并多余空格、

   必须连同 `_origin_ok` 一起改（源需求文档 §8 末段也点明这一点）。

## 11. 已知局限

1. **正文没有 git 历史。** 这是「不被构建覆盖、不被 `git pull` 回滚」的直接代价：`data/charter/`
   不入库。真正的版本记录只有本地 30 份滚动备份。**重要改动请自己导出一次 JSON。**
2. **不合并并发修改。** 两个标签页同时按保存，仍是一个赢一个 409。没有自动合并，也没有三方合并。
3. **`localStorage` 满时不保底。** 恢复副本写不进去时，界面会阻止「使用文件内容」并提示先导出，
   但不会替用户找地方存。
4. **`file://` 下只读。** 没有服务端，保存按钮置灰并说明原因；不假装成功。
5. **不校验语义。** 只校验结构与上限。写空话、写重复段落、写前后矛盾的条目，程序不管。
6. **备份不含时间机器。** 30 份之外的数据没有；一天内改 40 次会挤掉最早的 10 份。
7. **不支持多份宪法。** 想留一版「2026 冬季修订」，只能导出成文件自己管。

## 12. 待定问题

**Q1 两个站点（原站 AWE 与本终端）各存各的，用户会不会以为在同步？**
源需求文档 §7 明确「本期不要求实时同步」。但两边都叫「基金宪法」、都长得一样，
用户很可能在一边改完去另一边找。当前只在文档里写明，页面上**没有任何提示**。
建议：在本页加一行极淡的说明「本页正文只属于本机」，或干脆不做跨站迁移。**待定。**

**Q2 409 之后「用本页覆盖」是否该二次确认服务端最新版的内容？**
现在只 `confirm` 一次「另一页的修改会被替换掉」，不显示差异。要不要在确认框里列出
「对方的标题是 X，你的是 Y」？代价是要做一次 diff 展示，收益是用户能判断值不值得覆盖。**待定。**

**Q3 备份 30 份够不够？**
按「一天改三次」算是 10 天。但这个模块可能一个月改一次、一次改十条。
按份数滚动会在密集修改时把一次大改之前的版本挤掉。**候选方案**：改成「按天保留最近 30 天 +
每次保存都留」的双轨。**待定。**

**Q4 未应用的抽屉文字，恢复时该不该自动打开抽屉？**
现在会。好处是不会漏；坏处是用户可能只是刷新看一下，却被一个抽屉挡住。
替代方案：只在提示条上给「恢复未应用的输入」按钮。**待定。**

**Q5 目录的滚动点亮在长短不一的支柱上会跳。**
现在按「支柱顶端越过视口 1/3」判定。若某支柱只有一条短信条，滚过去时下一支柱很快接上，
目录会闪一下。**待定**：是否改成「取进入视口面积最大的支柱」。

**Q6 标题自动规则是否该连副标题一起管？**
现在副标题永远手填。若用户删成 9 条，标题变「投资信条」而副标题还写着 `V1.0`，
没有任何提示。要不要在条数变化时给一个「副标题是否也要改」的轻提示？**待定。**

**Q7 `path` 字段要不要从接口里去掉？**
它现在是排障用的（用户能一眼看到正文到底存在哪）。但对外部署时会暴露本机路径。
**待定**：改成只在 `source === "file"` 且请求来自 `127.0.0.1` 时返回。

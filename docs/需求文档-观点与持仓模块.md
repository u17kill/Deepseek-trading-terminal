## 0. 一页速览

顶部菜单第一层有五个分组，其中「观点」与「持仓」各管一件事：

- **观点**：别人怎么看。四页——市场新闻、专家观点、机构研报、财经日历。
- **持仓**：我怎么拿。两页——大佬持仓（别人的季报）、当前持仓（我自己的账）。

| # | 页面 | `pane` | hash | 组 | 回答什么 | 最小可用数据 |
|---|---|---|---|---|---|---|
| 1 | 市场新闻 | `pane8` | `#news` | 观点 | 最近一周世界上发生了什么 | 17 个 RSS / 快讯源 |
| 2 | 专家观点 | `pane7` | `#wind` | 观点 | 谁说了什么，立场偏哪边 | 127 人 / 458 条人写要点 |
| 3 | 机构研报 | `pane9` | `#research` | 观点 | 卖方与资管怎么判断，覆盖到哪 | 30 家 × 5 主题 / 67 篇 |
| 4 | 财经日历 | `pane12` | `#calendar` | 观点 | 接下来哪一天有事 | 377 条事件（到 2027-12） |
| 5 | 大佬持仓 | `pane10` | `#holdings` | 持仓 | 聪明钱季末拿了什么，这季动了什么 | 35 家 SEC 13F |
| 6 | 当前持仓 | `pane11` | `#portfolio` | 持仓 | 我自己拿了什么，结构有没有偏 | 卫星 52 张 + 核心 5 只基金 |

> 注意：**页签顺序与 DOM 顺序是两件事**。DOM 里 `pane7`（专家观点）物理位置在 `pane1`
> 之前，`pane11`（当前持仓）排在 `pane13` 之后。切换只靠 `data-p` 与 `display`，
> 不要按 DOM 顺序推断菜单顺序。

### 五条必须先知道的结论

1. **六页的内容来源有三种，不是一种。** 人写的（专家观点的要点、研报的论据、新闻的
   `why`、体检的判断）、规则拼装的（新闻的导语与头条排序、研报的统计、日历的当周切片）、
   机器搬运的（新闻原料池、专家观点的自动抓取标题）。**哪一句能信到什么程度，取决于
   它属于哪一种**，页面上必须能分辨。§5 有一张逐页对照表。

2. **只有两页的刷新会真去上网。** 市场新闻抓原料池，专家观点逐人检索标题；
   机构研报只重读本地 JSON，财经日历没有刷新按钮（每次 GET 现算）；大佬持仓抓 SEC；
   当前持仓没有刷新，它是本地文件的双向编辑。

3. **当前持仓是六页里唯一可写的页面。** 编辑先写浏览器草稿、再写回源文件（原子替换 +
   备份），其余五页全部只读。写回失败时数据不丢，但会退回「只在本机」状态，必须在页面上
   说清楚（§4.6.5）。

4. **「持有」与「观察」是两件事，「备注金额」不是市值。** 当前持仓汇总的是用户手填的
   仓位备注（`12k` = 12,000），不是市值、成本或盈亏。**整组六页里除了 13F 的季末申报表总值，
   没有一个「此刻」的市值数字**——大佬持仓的金额是季末快照，当前持仓的金额是手填备注。

5. **六页的数据时效差了两个数量级。** 新闻按小时（7 天窗口滚动）、专家观点按周
   （30 天体检线）、研报按月（窗口 2 个月）、日历按年（前瞻到 2027-12）、
   13F 按季（法定滞后 45 天，最长四个半月）、持仓是手填（改一次动一次）。
   **不要用同一套「数据过期」的判据去套六页**，§5.5 给了每页该看哪个时间字段。

## 1. 产品定位

### 1.1 两组的分工

一条完整的判断链有四步，这两组占中间两步：

| 步骤 | 问题 | 由谁回答 |
|---|---|---|
| 1 | 今天发生了什么 | 市场总览（`pane0`）、市场新闻（`pane8`） |
| 2 | **别人怎么想** | **观点组（`pane7/8/9/12`）** |
| 3 | **我在哪** | **持仓组（`pane10/11`）** |
| 4 | 接下来往哪偏 | 资产方向（`pane14`） |

「观点」不是「预测」。这一组收的是**已经说出口的判断**：谁在什么场合说了什么，
哪家机构在报告里给了什么结论，哪天有哪件事要发生。它不合成方向，不给目标价，
不做买卖建议。四页合起来的作用是让读者知道**自己跟市场共识差在哪里**。

「持仓」也不是「推荐」。大佬持仓是把 SEC 的公开申报翻译成人能读的卡片，
当前持仓是把用户自己手填的账整理成结构。两页放在同一组，是因为它们回答同一个问题的
两半：**别人的钱在哪，我的钱在哪，差多少**。

### 1.2 六页各自的分工

- **市场新闻（`pane8`）**：六页里唯一有「时效」概念的页面。7 天窗口滚动，过期的自动掉出去，
  哪怕是人写过的稿子也不留。两层内容分得很清：手写稿有 `why`（为什么重要），
  原料池没有 `why` 就标「未策展」，不装作有。
- **专家观点（`pane7`）**：127 位人物的表态库，每人一张卡，六类分组。核心是
  **人写要点**（谁在哪天说了什么、来源是哪），自动抓取的标题只作为「这人最近有动静」
  的旁证，绝不进多空温度条。
- **机构研报（`pane9`）**：30 家机构 × 5 个主题的覆盖矩阵。它不是「研报聚合器」，
  是**覆盖地图**：哪个主题有谁在写、哪一格是空的，空格本身就是信息。
- **财经日历（`pane12`）**：年 / 月 / 周三个视图，7 类事件、8 个市场。它唯一的硬要求是
  **确认度必须显形**：已确认、推测、待定三种状态在视觉上要能一眼分开。
- **大佬持仓（`pane10`）**：35 家机构的 13F 摘要 + 相邻两期逐项对比。它最重要的价值不是
  「谁买了什么」，是**「谁这个季度真动了」**——新进、增持、减持、退出，按股数判，不按市值。
- **当前持仓（`pane11`）**：三个视图（总仓 / 核心仓 / 卫星仓）。核心仓是「基金 → 资产」
  两层，卫星仓是「策略 × 主题 × 地区」的矩阵。总仓只做折算后的合并读数。

### 1.3 与相邻页面的边界

| 相邻页面 | 边界 |
|---|---|
| 市场总览（`pane0`） | 那边是「今天」的行情与一句话判断；新闻这边是「这一周」的事件流。两边的「重要」不是同一个尺子：总览看的是价格异动，新闻看的是事件本身 |
| 温度组（`pane1~6`） | 那边量的是冷热与估值，全是数字；这边量的是「谁说了什么」「我拿了什么」，全是内容。**不要拿专家观点的多空比去校验情绪温度**，两者样本完全不同（127 个有名有姓的人 vs 全市场 5,579 只股票） |
| 资产方向（`pane14`） | 那边是四层评分摊到 14 类资产的方向；观点组只提供「人说了什么」，不把人的话折算成分数 |
| 个人笔记（`pane13`） | 那边是用户自己写的泳道卡片；当前持仓是结构化的账。两者都会写盘，但一个写 `notes.json`、一个写 `matrix.json` / `core.json`，互不引用 |

## 2. 范围

### 2.1 本模块包含

1. 「观点」组四页与「持仓」组两页的**页面结构与导航**（含两个分组、六个 hash）。
2. 六页的**展示逻辑**：区块划分、排序、筛选、搜索、空状态、状态条、页脚口径。
3. 六页的**数据契约**：八份 JSON 的字段、写入方、校验规则、窗口与上限。
4. **十五个接口**：七个只读、四个刷新、两个进度、两个写回（§8）。
5. **判断与内容的来源纪律**：哪些字是人写的、哪些是规则拼的、哪些是机器搬的（§5）。
6. 当前持仓的**编辑与写回链路**：草稿、去抖、冲突裁决、原子替换、备份。
7. 34 条可判定的**验收标准**（§11）与 10 个**待确认问题**（§12）。

### 2.2 本模块不包含

| 不包含 | 理由 |
|---|---|
| 交易执行、下单、券商对接 | 这是看板，不是交易终端。全项目没有一条下单路径，也不该有 |
| 实时行情报价 | 六页里没有一个数字需要秒级刷新。13F 是季度数据，新闻最快也是分钟级 |
| 组合优化、再平衡建议、目标价 | 判断由人写（体检卡里的「如果只动三处」是人写的，不是算出来的）。程序只负责把读数摆到目标区间旁边 |
| 新闻正文抓取与摘要生成 | 只搬标题、首段、链接。正文抓取涉及版权，摘要生成会污染「谁说的」这条链 |
| 估值 / 情绪 / 动能的算法 | 归温度组（`pane1~6`）。本模块只消费 `review.json` 里引用的 `env_asof` 日期 |
| 个人笔记 | 归工具组（`pane13`）。虽然也写盘，但结构与用途完全不同 |
| 真实市值、成本、盈亏 | 当前持仓汇总的是仓位备注（`12k`），不是持仓市值。要算盈亏得有成交记录与行情，本项目没有 |
| 港股 / 日股的机构持仓披露 | 13F 只覆盖在美申报主体。港股权益披露（SFC）、日本大量保有报告口径不同，不在本轮 |

## 3. 页面结构与导航

### 3.1 两层菜单

第一层五个分组，第二层是该组的页签。**只有当前组的页签可见**，其它组的按钮用
`display:none` 隐藏（不是移除 DOM）。

| 第一层 | `data-g` | 含页 |
|---|---|---|
| 市场 | `mkt` | 市场总览(0)、资产方向(14)、市场新闻(8) |
| 观点 | `view` | 专家观点(7)、机构研报(9)、财经日历(12) |
| 持仓 | `pos` | 大佬持仓(10)、当前持仓(11) |
| 温度 | `temp` | 动能(1)、估值(2)、A股(3)、美股(4)、港股(5)、亚太(6) |
| 工具 | `note` | 个人笔记(13) |

三条硬要求：

1. **`data-g` 的值是 `mkt / view / pos / temp / note`，不是 `market`。** 这个项目踩过一次：
   探针点了 `data-g="market"`，选择器什么都没匹配到，点击静默无效，看起来像「切组坏了」。
2. **市场新闻的 `data-g` 是 `mkt`，但它按内容属于「观点」。** 这是历史上的物理位置，
   本版不改（改它要动第一层菜单的语义，收益不值）。文档按内容把它算进观点组，
   实现方若要重排，把它的 `data-g` 改成 `view` 即可，其余不用动。
3. **切组要记住上次停留的页。** 在「温度」里常看港股，切出去看新闻再回来，
   不该被扔回组内第一页。状态记在内存（`MNAV_LAST`），**不持久化**——刷新后回到第一页，
   这是有意的：持久化会让「打开看板」这件事失去确定的落点。

### 3.2 hash 路由

```
#news 8   #wind 7   #research 9   #calendar 12
#holdings 10   #portfolio 11
```

- 六页的 hash **双向可查**：地址栏输入直达，点页签回写地址栏。
- 回写用 `history.replaceState`，不用 `location.hash =`——后者会进历史栈，
  点三次页签要按四次后退才能离开。
- 认不出的 hash 落到市场总览（`pane0`），因为它是「今天发生了什么」的默认答案。
- `hashchange` 必须监听：用户手改地址栏后要能切页。

### 3.3 六页骨架

六页结构不同，但都遵守同一套自上而下的三段式：

```
页首条 / 头部（数据日期 · 规模 · 口径 · 刷新按钮 或 免责说明）
        ↓
主体（这页真正的内容，按 sec 分块，每块一个 sec-h 标题 + note）
        ↓
页脚 / 注脚（口径、禁止事项、数据来源）
```

差异只在这三段的重量：

| 页 | 头部 | 主体块 | 页脚 |
|---|---|---|---|
| 市场新闻 | 主轴条 + 「更新新闻」 | 本期主轴 / 头条 / 分类流 | 无（口径写在各块 note 里） |
| 专家观点 | 本期主线 + 「更新观点」 | 本期主线 / 立场分布 / 人物卡片 | 无（每张卡自带来源） |
| 机构研报 | 状态条（覆盖数 + 「刷新研报」） | 覆盖矩阵 / 按主题读 | 无 |
| 财经日历 | 无头部 | 当周核心事件 / 日历（年·月·周） | 收录口径（「没收录不等于没发生」） |
| 大佬持仓 | 头部说明（三条免责）+「更新持仓」 | 季度变化 / 机构目录 + 详情抽屉 | 口径写在详情卡与外链区 |
| 当前持仓 | 视图切换 + 导出/导入 | 总仓视图 / 卫星仓矩阵 / 核心仓 | 口径长注（金额怎么算、什么不计入） |

**每页都必须有一个「当前数据是什么时候的」入口**，且这个日期要来自数据，不来自抓取时刻。
§5.5 给了六页各自该用哪个字段。

### 3.4 响应式

断点六档，六页共用：

| 断点 | 变化 |
|---|---|
| ≤ 1200px | 页签栏收窄，次要按钮换行 |
| ≤ 1100px | 部分三列网格降为两列 |
| ≤ 980px | 大佬持仓：详情抽屉从侧栏改为点击展开、页内滚到详情；当前持仓总仓单列 |
| ≤ 900px | 市场新闻的头条区与分类流从两列降为单列 |
| ≤ 720px | 研报覆盖矩阵横向滚动，机构列固定 |
| ≤ 620px | 当前持仓收窄名称列；表格数字字号下调一档 |

**不要新造断点。** 六页共用这一套，加一个 640px 会让相邻两页在同一个窗口宽度下表现不一致。

### 3.5 本地状态

六页里只有三处会把状态写进浏览器：

| 键 | 写入方 | 内容 | 生命周期 |
|---|---|---|---|
| `hld_snap_v1` | 大佬持仓 | 最近一次核对成功的完整 13F 快照 | 持久；与内嵌快照按 `built_at` 比新旧，取新的那个 |
| `pmx_map_v1` | 当前持仓（卫星仓） | 用户编辑后的卫星仓草稿 | 持久；键名不能改，改了用户现有草稿就丢了 |
| `pmx_core_v2` | 当前持仓（核心仓） | 核心仓草稿 | 持久；v1 → v2 是因为结构从「矩阵」改成「基金 → 资产」 |
| `pmx_mode` | 当前持仓 | 上次看的视图（`total` / `core` / `sat`） | 持久 |

其余状态（搜索词、立场筛选、日历视图与翻页位置、研报的机构/主题筛选）**一律不持久化**。
理由：这些都是「这一眼在看什么」，记住它们会让下次打开时呈现一个用户没预期的筛选结果，
而用户往往不会意识到是筛选在起作用。

### 3.6 `file://` 打开时的行为

看板可以双击 HTML 直接打开（不启服务），六页的表现不同，必须逐页说清：

| 页 | `file://` 下 |
|---|---|
| 市场新闻 | 看得到构建期快照；点「更新新闻」会失败，结果条写「连不上本地服务」 |
| 专家观点 | 同上；「更新观点」失败，错误条显示原因 |
| 机构研报 | 「刷新研报」失败（它要 POST）；矩阵与卡片正常 |
| 财经日历 | **完全正常**。数据全部内嵌，没有任何请求 |
| 大佬持仓 | 只读正常（快照内嵌）；「更新持仓」失败 |
| 当前持仓 | **能编辑，但写不进文件**：草稿存本机 localStorage，工具条显示「未连本地服务 · 改动只在本机」，并给「导出 JSON」按钮 |

当前持仓这一条是全项目最容易误解的地方，页面上必须显式提示，不能只把按钮变灰。

## 4. 功能需求

### 4.1 FR-1 市场新闻（`pane8` / `#news`）

#### 4.1.1 页首状态条

一行说清五件事，缺一件读者就会误判：

```
100 条 · 头条 8 条 · 未策展 100 条　·　窗口 近 7 天 11-17 ~ 11-24　·　原料池 426 条，过期 76 / 超额 294 未上屏
```

- 「过期」= 手写稿过期 + 原料过期，两个数相加后再显示。
- 「超额」= 达到单桶/单条上限被截掉的条数（`n_drop.capped`）。**必须显示**：
  不显示的话，用户会以为「这一周就这么点事」。
- 刷新完成后，这一行**追加**一段「已重抓 HH:MM:SS（N.Ns）：上屏 X 条（未策展 Y），
  过期丢弃 Z 条、超额 W 条，静态页已重建 / 页面重建失败」。

#### 4.1.2 本期主轴（`brief`）

- 手写导语只在 **48 小时**内有效。超过 48 小时即使文件里还留着，也不显示——
  导语写的是「当天的判断」，挂到六天后就是误导。
- 手写导语过期时，**退到自动摘要**，不允许留空。自动摘要必须带一个明显的标识块：
  「自动摘要」+ 规则原文（「取头条带前五，不足则按时效 · 同报家数 · 是否人写补齐，
  每桶最多一条；一句话取自原文首句，未改写」）。
- 两条都不存在时（连原料池都空），显示一句明确的话：「本期没有手写导语」+ 解释为什么
  宁可空着也不拼一句——判断这句「为什么」程序造不出来。

#### 4.1.3 头条

- 8 条上限（`CAP_TOP`），带序号 `01`~`08`。
- 排序**不按时间**：先按重要性分数排，同分时新的在前。理由：一条 6 天前的手写头条压在
  今天的新闻上面，第一眼就误导。
- 标「持续」的条目（`carry`）是仍在发酵的大事件，允许落在头条窗口外。
  **上限 2 条**，超了校验告警。
- 每条卡片：标题、90 字摘要、`why`（人写才有）、来源、时间、同报家数、原文链接、
  影响面标签（股 / 债 / 汇 / 商品 / 加密）。
- 原料池来的卡片右上角标「未策展」，鼠标悬停写「原料池直接搬运，没有人工判断」。

#### 4.1.4 分类流

七个桶，顺序固定：宏观政策、地缘与贸易、美国国内、中国国内、AI 与科技、传统产业、快讯流。

- 单桶上限 12 条，快讯流 40 条。
- 手写稿优先占位，自动条目补位（稳定排序：先手写后自动，组内维持原序）。
- 桶内按时间倒序。
- **空桶不隐藏**，显示「窗口内无重大事项——不凑数」。这一句比留白重要：
  2026-11-15 那一版「传统产业」就是 0 条。
- 去重：手写稿已覆盖的事件，原料池里同一件事不再出现（标题相似度 ≥ 0.42 视为同一件）。

#### 4.1.5 陈旧提示条

页面最新一条距今超过 **12 小时**时，页首下方出现黄色条：

> 页面最新一条是 N.N 小时前：窗口按最近 7 天滚动，过期的会自动掉出去。点右上「更新新闻」重抓原料池。

这条按**浏览器当下时间**算，不用构建期快照——否则页面越放越「新」。

#### 4.1.6 「更新新闻」

同步请求，最长约 20 秒（17 个源串行 + 聚簇 + 合成 + 重建页面）。

- 按钮文案：`更新新闻` → `抓取中…` → 回 `更新新闻`。
- 成功后用返回的数据重渲染整页，并在状态条上追加本轮统计。
- 失败不覆盖旧数据，在提示条位置显示红色错误条，原文前 60 字。

### 4.2 FR-2 专家观点（`pane7` / `#wind`）

#### 4.2.1 页首

一行四段，少一段就会出现误读：

```
主线 10 条（1 条超上限未显示）　·　127 位 / 458 条要点　·　最近一条 11-08　·　另有自动抓取 503 条（116 位 · 抓于 11-16）　·　窗口 08-01 ~ 11-16
```

- **「最近一条」不是窗口末端。** 窗口末端是人写死的快照日（`as_of`），它不会自己往前走；
  `latest_point` 才是内容真实的新鲜度。2026-11-15 点开看到「截至 11-08」，
  才知道这一周没人补内容。
- 超上限的条数必须写出来（例：`（1 条超上限未显示）`），悬停列出被挤掉的标题。
  **静默丢弃策展内容是禁止的。**

#### 4.2.2 本期主线

- 最多 10 条（`BRIEF_MAX`），按人写的顺序（顺序即重要度）。
- 超出部分不删数据：截断后把标题放进 `brief.dropped`，页面注明条数。
- 每条：序号 `01`~`10`、标题（`h`）、正文（`t`，通常 150~300 字）。

#### 4.2.3 立场分布

六类各一格：宏观大师、价值投资、科技投资人、科技与产业、央行与监管、政府。

- 每格一根三段条：绿=偏多、红=偏空、灰=中性，宽度按人数占比。
- 格内文字：`N 人 · M 条`；有自动抓取时追加 `· 自动 K`。
- 点击整格滚到该分类的卡片区。**如果当前筛选把目标块过滤没了，先清筛选再跳**，
  并在计数行写清「已清除筛选」——跳不过去比丢一次筛选更糟，但静默改状态也不行。
- 自动抓取的条数**不进多空条**。机器搬来的标题没有立场，让它进多空比就是替人下判断。

#### 4.2.4 人物卡片

按分类分区，分类内按 `grp` 再分子组（有子组才分）。每张卡：

```
头像（首字）  姓名（中文） / 英文名   立场标签
角色 · 机构
一句话立场（stance）
要点 1：日期  来源  正文
要点 2：…
最近表态（自动抓取）：日期 标题 来源↗     ← 最多 5 条，标「自动抓取 · 原文标题」
```

- 搜索框匹配人名、英文名、机构、角色、要点正文、立场、分组名。
- 立场筛选：全部 / 偏多 / 中性 / 偏空。
- 「只看结论」开关：只显示每条要点列表的第一条（不是隐藏立场句）。
  切换后按钮文案变「展开全部要点」。
- 卡片计数行：`显示 N / 127 位，M 条要点，K 条自动抓取`。

#### 4.2.5 陈旧与空缺

- 每人最近一条**人写**要点距今超过 **30 天**，进陈旧清单。页首下方黄色条列出前 10 位
  （`姓名 N天`），超过 10 位写「等 N 位」。
- 有自动抓取的人，括号里补「（自动 MM-DD）」，让读者知道该补的是**判断**还是**压根没人报道**。
- 完全没有要点的人单独计数。

#### 4.2.6 「更新观点」

后台任务 + 轮询，40~60 秒。

- 按钮文案随进度变化：`更新观点` → `检索中…` → `检索 37/127` → 完成回 `更新观点`。
- 轮询间隔 700ms，最多 400 次（约 280 秒）。
- 完成后结果条必须说三件事：**新增几条、谁那里多了、谁没搜到**。
  只说「已重载」的话，用户看到满屏没动的卡片，只会以为按钮坏了。
- 结果条同时写「自动合计 N 条（M 位，最近 MM-DD）」与「人写的 N 条没动」。
- **自动抓取永不修改人写要点、不修改立场标签**。

### 4.3 FR-3 机构研报（`pane9` / `#research`）

#### 4.3.1 状态条

```
覆盖 30 家机构 ｜ 67 篇报告 ｜ 窗口 2026-09-01 ~ 2026-11-02 ｜ 口径 主题 × 机构（同一格可多篇）
                                          62 个格子有稿 · 共 150 格      [刷新研报]
```

#### 4.3.2 覆盖矩阵

- 行 = 机构，按国家分组（北美 → 欧洲 → 亚太）；组标题后跟类型统计（`投行 7 · 资管 4 · 科技 2`），
  **机构数少于 4 家时不写**，免得噪音。
- 列 = 5 个主题：宏观、市场、特殊资产、AI 产业、其他产业。
- 格子三种状态：**实心（本期有稿，标立场色）** / 数字（同格多篇，显示篇数）/ 点 `·`（无稿）。
- **空格不隐藏**：「谁没覆盖哪个主题」本身是信息。
- 行尾显示覆盖率 `N/5`。
- 点格子 → 只看这一格（机构 × 主题）；点机构名 → 只看这家。两者可叠加。

#### 4.3.3 按主题读

- 主题导航（chips）：全部 + 5 个主题，各带篇数。
- 搜索匹配：标题、结论、范围、目标、要点全文、机构中英文名。
- 筛选状态条：`正在看：高盛 × 宏观`，带「清除」。
- 计数行：`显示 N / 67 篇，M 家机构`。
- 每张报告卡：机构（中英）+ 范围 + 日期（`MM-DD`）、标题、结论（`thesis`）、
  1~4 条要点、目标（`call`）、立场标签、来源（`src`）。
- 筛选结果为空时，写「当前筛选下没有报告。点『看全部』恢复全量」，不写「暂无数据」。

#### 4.3.4 「刷新研报」

同步，1~3 秒（重读 JSON + 校验 + 重算统计 + 重建页面）。

- 校验不过一律拒渲染：返回 400，把前 5 条错误原文带回页面。
  **不允许「部分渲染」**——半份数据比报错更难查。
- 成功后在状态条上写时间。

### 4.4 FR-4 财经日历（`pane12` / `#calendar`）

#### 4.4.1 当周核心事件

- 一周七天横排，今天高亮。
- 每天最多显示 3 条起始事件，其余折叠成「还有 N 条」。
- **跨日事件按 id 去重**：一个连开四天的会，七天里数出来是 4 条，读者数的是 1 件。
  去重后与「本周几件事」对齐。
- 从上周延续过来的（全程是「延续」状态）不每天占一行，改为当天写「持续中 N 项」，
  悬停列出名字；一周结束后统一列一次。
- 每天显示 `pri=1` 的事件数（高优先级）用于「这周有几天是真有事」的判断。

#### 4.4.2 日历视图

- 三个缩放：年 / 月 / 周。翻页按视图步长（年 ±1、月 ±1、周 ±7），「今天」回到当下。
- **年视图**：12 个月格子，每月显示事件数与前 2 条；点月份进月视图。
- **月视图**：日格 + 事件条，超出显示「还有 N 条」；点「还有 N 条」进周视图。
- **周视图**：七天列，显示全部事件与时间。
- 图例 7 类，可点击开关（关掉的类型不渲染，不是变灰）。

#### 4.4.3 确认度必须显形

| 状态 | 视觉 | 含义 |
|---|---|---|
| `confirmed` 已确认 | 实色 | 官方日程已公告 |
| `estimated` 推测 | **斜纹底 + 虚线左边框** | 按惯例推出，官方未公告；悬停显示依据（`note`） |
| `tbd` 待定 | 虚线框 + 空心 | 官方只给了季度/月份 |

页脚必须写：`收录口径：美 / 中 / 港 / 台 / 日 / 韩核心公司与全球产业大会；财报覆盖
「七巨头 + 台积电 + 三星 + 海力士 + 阿斯麦 + 博通」每家每季，其余按影响力择要——
**没收录不等于没发生**。`

#### 4.4.4 没有刷新按钮

日历是人查证后写进 JSON 的静态策展数据，没有「抓取」这一步。所以：

- 页面不放刷新按钮（放了会让人以为能抓到最新公告）。
- `GET /api/calendar` 每次**现算**，改完 JSON 刷新页面就能看到。
- 页脚显示「数据截至 YYYY-MM-DD」。

### 4.5 FR-5 大佬持仓（`pane10` / `#holdings`）

#### 4.5.1 头部三条免责

必须在正文之前，用正常字号的段落，不能用小灰字：

> 这里是 SEC 13F 的公开申报摘要。在美国管理股票超过 1 亿美元的机构，须在每季结束后
> **45 天内**披露该季度末持有的美股多头与期权。所以它**不是实时持仓**（最长滞后四个半月）、
> **不是完整组合**（现金、债券、非美股票与空头都不在表里）、**也不是交易信号**——
> 它只说明「季末那一天账上有什么」。

#### 4.5.2 状态条

```
已核对 35 家 ｜ 成功 35 ｜ 主要报告期 2026Q2（18 家）· 另有 3 个季度 ｜ 数据源 SEC EDGAR 13F
                                                          快照 2026-11-16
```

**「主要报告期」取家数最多的那个季度，不是最新季度。** 本期 18 家在 Q2、15 家在 Q3，
取最新会显示「2026Q3」，读者会以为 35 家都交了 Q3——这类静默误导比缺一个数字更糟。

#### 4.5.3 季度变化

回答两个问题：谁有可比的上期、谁这个季度最坚决。

- 第一行：`N 家有可比的上期，另 M 家没算（原因见下）`。
- 按「哪两期比」分组，显示 `2026Q1 → 2026Q2  17 家`。当前四组：
  `2026Q1→Q2` 17 家、`2026Q2→Q3` 15 家、`2025Q2→Q3` 1 家、`2023Q2→Q3` 1 家。
- 每家只取**它自己最大的一次权重变动**，横向排前 6：机构名、动作标签（新进/增持/减持/退出）、
  发行人、权重变动 pp。
- **不同规模的组合只能比相对自己的占比**，直接比金额会变成比谁盘子大。
- 没算的家要写原因：两期总值差 N 倍（不是同一个组合）、无上期、解析失败。

#### 4.5.4 机构目录

- 五组：价值与质量(12)、主动与特殊机会(3)、成长与科技(11)、宏观与多策略(7)、量化与系统化(2)。
- 组标签带家数；「全部」也带总数。
- 搜索：机构名、英文名、人物、CIK、申报主体名。
- 卡片：名称、英文名、人物、报告期（`2026Q2`）、状态徽标（修正 / 代报 / 历史）、
  申报表总值、证券数、当期最大持仓。
- 点卡片 → 右侧详情（≤980px 时改为页内展开并滚到详情）。目录不消失。

#### 4.5.5 详情

六格读数：报告期末（+ 季度）、实际提交日、申报项数（行）、期权项数、非期权证券（只）、
申报表总值（美元）。

四种旗标，各有颜色与固定文案：

| 旗标 | 触发 | 文案要点 |
|---|---|---|
| 本次核对失败（灰） | `carried` | 显示的是上一次成功快照：`2026Q2` |
| 历史申报（中性） | `stale`（报告期 > 400 天） | 「这不是当前仓位，也不能据此推断它现在在看多还是看空」 |
| 代报（灰） | `proxied_by` | 「最新提交为 13F-NT（通知），持仓由公开母公司 X 代报；通知不等于空仓」 |
| 修正申报（蓝） | `amended` | 「会整体替换同一报告期的原申报；原申报的数字不应再被引用」 |

- **机构说明**（`about`）显示在头部下方。这是人写的一段话，解释为什么归这一组、
  这家有什么要留神（例：GQG 前十大单季换 8 只仍归价值，因为看的是方法）。
- 持仓列表：按市值倒序取前 12 项非期权证券。每行：发行人、类别、CUSIP、股数、市值、
  占比条（以第一名为 100% 归一）。
- 期权注：申报含期权时写「本申报含 N 项期权（PUT/CALL），已单列、不进入下面的列表。
  但**占比分母用的是申报表总值，包含期权**，所以这里的占比不是纯股票多头权重」。
- 外链三个：SEC 原件、13f.info 转录、该机构全部申报。

#### 4.5.6 与上一期相比（详情内）

- 计数徽标：新进 / 增持 / 减持 / 退出 / 未动。
- 逐项列表最多 10 条（`CHG_KEEP`），按权重变动绝对值排序，只列有动作的。
- 每条：动作标签、发行人、权重变动 pp、股数变动、权重前后、`疑拆股` 标记。
- **股数变动超过 10 倍（`|sh_pct| > 900`）时改印两期绝对股数**：
  「148 股 → 695.4 万股」。否则会出现 +470 万% 这种没人读得懂的数字。
- 不可比时（两期总值差 4 倍以上）**不给逐项列表**，只写清倍数、两期总值、两期证券数，
  并说明「这是换了个簿子，不是调仓」。
- 上期不是紧邻季度时写「中间缺 N 个季度，变动是跨 N 个季度的累积」。
- 上期是增量修正（NEW HOLDINGS）时不当基准，换再上一期，并在注里说明。

#### 4.5.7 「更新持仓」

后台任务 + 轮询，35 家 × 两份申报约 280 秒。

- 按钮文案：`更新持仓` → `核对中…` → `核对 12/35` → 完成。
- 逐家失败不用错误覆盖整页：**沿用上一次成功快照**，状态标 `carried`，
  详情里写清「本次核对失败（原因），下面是 2026Q2 的快照」。
- 完成后快照写 localStorage（键 `hld_snap_v1`），并按 `built_at` 与内嵌快照比新旧。

### 4.6 FR-6 当前持仓（`pane11` / `#portfolio`）

这是六页里唯一可写的一页，也是最复杂的一页。

#### 4.6.1 三个视图

| 视图 | 币种 | 可编辑 | 内容 |
|---|---|---|---|
| 总仓（默认） | 人民币 | 否 | 核心 + 卫星合并读数、三种切法、持仓体检 |
| 核心仓 | 人民币 | 是 | 基金 → 资产 两层，基金 5 只 / 资产 15 项 |
| 卫星仓 | 美元 | 是 | 策略 × 主题 × 地区 矩阵，52 张计入卡片 |

- 视图选择持久化（`pmx_mode`）。
- 总仓的工具条不给「添加标的」，只给「导出 / 导入」。
- 切到某仓时，该仓的草稿与本机时间单独加载，**两个仓的草稿不能互相覆盖**。

#### 4.6.2 卫星仓

矩阵：列 = 主题（挂在策略下，共 15 个），行 = 地区（美国、中国、日韩台印、欧洲、其他）。

- 卡片：代码、名称、金额备注（`12k`）、状态色。
- 四种状态：已持仓 `held`、观察中 `watch`、计划加仓 `add`、期权 `option`。
- **只有 `held` 与 `add` 参与合计**，且金额必须写成完整「数字 k」。
- 观察中、期权不进普通合计；纯文字、`put 115`、区间 `2.7k–5`、无 k 的裸数字一律
  「不可计算」——**既不计入，也不当作 0**。
- 期权另列（蓝虚线框），永不并入普通仓位金额；备注里出现 put/call **不会**自动改状态。
- 未归类卡片（`columnId` 为空）：卡片还在、金额还在，但不进任何合计与三种拆分。
- 顶部工具条：卡片数 / 计入 / 观察 / 期权 / 备注不可计算 + 存盘状态徽标 + 「+ 添加标的」。
- 搜索（代码、公司名、备注）、密度切换（紧凑 / 舒适）。
- 汇总区：三种拆分（策略 / 地区 / 主题）三列，右列同为 Σ，**彼此不可相加**。
- 页脚口径必须写：合计只累加「已持仓 + 计划加仓」中完整写成「数字 k」的备注，
  1k = 1,000 美元，**Σ 是备注合计，不是资产价值**；日韩台印是合并地区，不构成国别统计。

#### 4.6.3 核心仓

结构是两层：**基金（名称 + 金额）→ 资产（名称 + 国家 + 风格 + 权重）**。

为什么不能单层：一只「多策略基金」里装着红利 40% / 商品 50% / 黄金 10%，国家与风格落在
**资产**这一层，不落在基金上。统计一律按资产层：基金金额按权重切开，再按国家/风格/资产名聚合。

权重规则三种状态，页面必须标出来：

| 状态 | 触发 | 处理 | 页面标注 |
|---|---|---|---|
| `weight` | 全部填写 | 按权重归一（不要求凑满 100） | 无 |
| `partial` | 部分填写 | 没填的按剩余份额等分（0 与「没填」不是一回事） | 「部分权重，其余等分」 |
| `equal` | 一个都没填 | 按资产个数等分 | 「权重未填，按个数等分」 |

金额切分：整数分逐项向下取整，余数补到金额最大的那一份，保证 Σ 恰等于基金金额。
**不允许出现分位级别的四舍五入误差**（300 万分出 1 分的零头，会让总额对不上）。

#### 4.6.4 总仓

- 折算：`总仓 = 核心仓（人民币）+ 卫星仓（美元 × 7.00）`。
- **汇率固定 7.00，不取实时价。** 理由：汇率一动，历史合计就跟着变，月度对比立刻失去意义。
  即期汇率只在体检卡里做一次「记账口径 vs 今天能换回多少」的对照，不参与任何合计。
- 总仓三块：合计与两个仓的占比、三种切法（策略 / 地区 / 资产类别）、持仓体检。
- 资产类别合并规则写死：核心仓资产名里带「股票」的并成一项「股票」；卫星仓整仓记作
  「股票」（不拿主题冒充资产类别）。页面与后端必须用同一套规则，否则表格与图对不上。
- 地区别名必须合并（核心 `china/hk` → 中国；`jp/asia` → 日韩台印），否则「中国」会少一块。

#### 4.6.5 编辑与写回

链路：**改卡片 → 600ms 去抖 → 写草稿 → POST 源文件 → 徽标更新**。

1. 每次编辑**先写 localStorage 草稿**（毫秒级，断网也在），再写源文件。
   只写浏览器等于把数据押在「用户不清缓存」上，不能接受。
2. 写源文件前 600ms 去抖；**快照与目标仓必须在排定时就定下来**，不能在定时器里现取——
   去抖期内用户可能切了视图，现取会把卫星仓的数据写进 `core.json`。
3. 服务端：校验 → 备份（`data/portfolio/backups/`，滚动 30 份）→ 临时文件 → 原子替换。
   校验不过返回 400，**不写半份**。
4. 徽标七态：`正在读取源文件…` / `有改动，准备写回…` / `正在写回源文件…` /
   `已写入源文件 · 时间` / `未连本地服务 · 改动只在本机` / `写回失败 · 草稿还在本机` /
   `草稿也没写成 · 只在当前页`。
5. **冲突要显形**：本机草稿时间与源文件时间不一致时弹横幅，让用户选「用本机覆盖文件」
   或「用文件覆盖本机」，另一份先备份。不允许静默取一边——静默取错的那一边，
   表现就是「明明改过了，刷新还是旧的」。
6. 冲突标记要记在**仓**上，不能只记在当前视图上：启动时视图是总仓，
   若那时把提示吞掉，切到该仓时提示已经没了。

#### 4.6.6 持仓体检

位置：总仓视图下方。它**不是这张表的总结，是对这张表的判断**。左右分工必须写清：
**右边是算的，左边是写的。**

右边七个读数（全部实时算，随卡片改动立刻变）：

| key | 名称 | 算法 | 目标区间 | 2026-11-24 实测 |
|---|---|---|---|---|
| `region.cn` | 中国（含港） | 总仓中 `china + hk` 占比 | 28~40% | 33.6% 区间内 |
| `style.attack` | 进攻 | 总仓策略占比 | 35~45% | 44.8% 区间内 |
| `style.balance` | 均衡 | 同上 | 18~28% | 12.5% **欠 5.5pp** |
| `style.defense` | 防御 | 同上 | 30~45% | 42.7% 区间内 |
| `band.real_def` | 真防守 | 国债+黄金+中性+套利+CTA | 28~40% | 33.9% 区间内 |
| `factor.ai` | AI / 半导体因子 | 卫星 AI 主题 + 纳指100 + 标普500×⅓ | 15~25% | 32.5% **超 7.5pp** |
| `conc.top5` | 前五集中度 | 卫星仓前五 / 卫星仓（**分母是卫星仓**） | 0~40% | 23.9% 区间内 |

三条口径必须写在页面上：

- **真防守 = 国债 + 黄金 + 股指中性 + 期权套利 + CTA。红利与可转债是低 beta 股票，不算。**
- **AI 因子 = 卫星 AI 主题 + 纳指 100 + 标普 500 × ⅓**（标普里科技约三分之一）。
- **前五占比的分母是卫星仓，不是总仓。**

左边是人写文字（`review.json`）：当前情势（tag + line + 依据 5 条）、结构判断
（tag + line + note）、4 条问题（严重度 + 事实 + 为什么）、3 条「如果只动三处」
（方向 + 内容 + 区间 + 理由 + 触发条件）、3 条「另外盯住」、4 条「会让它作废」。

**过期报两种，缺一不可**：

| 判据 | 文案 |
|---|---|
| `as_of` 距今 > 30 天 | 「判断写于 N 天前，宏观的时效比仓位短，该重写了」 |
| 总仓相对 `anchor.total_wan` 漂移 > 10% | 「总仓相对写判断时（¥819.7 万）变了 ±X%，前提已经不同」 |

第二种比第一种重要：**这不是数字过期，是前提过期**——整段话是照着某个仓位形状说的，
形状变了，结论就没有依据了。

## 5. 内容口径（这是这一组最特殊的地方）

### 5.1 三种内容来源

| 页 | 人写的 | 规则拼装的 | 机器搬运的 |
|---|---|---|---|
| 市场新闻 | `issue*.json` 的 `why`、标题、分桶 | 导语（无手写时）、头条排序、同报家数 | 原料池 426 条（标「未策展」） |
| 专家观点 | 127 人的 `stance` + 458 条要点 | 分类统计、陈旧清单 | 503 条自动抓取标题（标「自动抓取」） |
| 机构研报 | 67 篇的 `thesis` / `pts` / `call` / `src` | 覆盖数、格子数、分组统计 | 无 |
| 财经日历 | 377 条事件（人查证后写 JSON） | 当周切片、月度展开、统计 | 无 |
| 大佬持仓 | 35 家的 `about` 说明 | 聚合、两期对比、旗标 | SEC 13F 原始申报 |
| 当前持仓 | `review.json` 的判断文字 | 七维读数、汇总、折算 | 无 |

### 5.2 判断不由程序拼装

这是全项目的第 14 条红线。在本组的具体含义：

- 新闻的 `why`（为什么重要）**只能人写**。程序没有 `why` 就标「未策展」，不生成。
  自动摘要里的每一句都是原文首句，**不改写、不压缩**——把两句并成一句就是替作者下判断。
- 专家观点的 `stance`（一句话立场）与要点正文**只能人写**。自动抓取的标题原样显示，
  不加工成「某人认为…」。
- 研报的 `thesis` 与 `pts` **只能人写**。检索只能拿到标题，论据要人读原文后写。
- 体检卡的判断文字**只能人写**。数字每天在动，观点得有人负责。
- 日历的 `src`（出处）与 `note`（依据）**只能人查**。推测项没有依据就不许标 `estimated`。

反面要求同样硬：**不要在这些地方加原文没有的判断词**（「建议」「值得关注」「利好」）。
多一个词，这一块就从「陈述」变成了「建议」。

### 5.3 两层内容必须能分辨

新闻与专家观点都是「人写 + 机器搬」并存，页面上必须一眼分清：

| 层 | 视觉标记 | 位置 |
|---|---|---|
| 人写（curated） | 无标记，带 `why` | 头条、六桶 |
| 机器搬（auto） | 卡片角标「未策展」，浅底 | 六桶、快讯流 |
| 人写（points） | 日期 + 来源 + 正文 | 人物卡片正文区 |
| 机器搬（feed） | 独立小块「最近表态 · 自动抓取 · 原文标题 · 抓于 MM-DD」 | 卡片底部 |

**两套数据不能合并存储。** `points` 与 `feed` 混在一个数组里，重抓一次就把人写的东西冲掉
——这正是这个项目最不能丢的部分。

### 5.4 五种「时间」，别用错

| 字段 | 含义 | 该用在哪 |
|---|---|---|
| `as_of` | 快照日 / 数据截至 | 页面「数据截至」、判断过期 |
| `generated` | 抓取时刻 | 「什么时候抓的」、过期条 |
| `updated` | 人工更新时刻 | 状态条 |
| `built_at` | 快照写入时刻（到秒） | **localStorage 新旧比较只能用这个** |
| `feed_fetched_at` | 自动抓取时刻 | 自动块角标 |

四条纪律：

1. **「数据日期」必须来自数据，不来自抓取时刻。** 2026-11-06 的数据在 11-08 抓，
   页面写 11-06。
2. **窗口末端不是新鲜度。** `window` 是人写死的快照日，内容可能一周没动。
3. **同日两次抓取只能靠 `built_at` 区分**，只比 `as_of` 会让浏览器里的旧快照顶掉新的。
4. **新闻的时效按浏览器当下算**，不用构建期时间，否则页面越放越「新」。

### 5.5 窗口与上限总表

| 项 | 值 | 出处 |
|---|---|---|
| 新闻窗口 | 7 天滚动 | `news.WIN_DAYS` |
| 新闻手写导语 | 48 小时 | `news.compose` |
| 新闻单桶 / 快讯 / 头条 | 12 / 40 / 8 | `CAP_BUCKET` / `CAP_WIRE` / `CAP_TOP` |
| 新闻源僵尸判定 | 最新一条 > 96 小时 → 整源不收 | `news.fetch` |
| 专家观点主线 | 10 条 | `wind.BRIEF_MAX` |
| 专家观点陈旧线 | 30 天 | `wind.freshness(days=30)` |
| 自动抓取窗口 | 21 天 | `windfeed.DAYS` |
| 自动抓取每人 / 每天 | 5 条 / 1 条 | `CAP` / `DATE_CAP` |
| 研报要点数 | 1~4 条 | `research.validate` |
| 日历前瞻 | 到 2027-12-31 | `calendar.range` |
| 日历跨期告警 | > 14 天 | `econcal.validate` |
| 13F 法定滞后 | 45 天 | SEC 规则 |
| 13F 历史判定 | 报告期 > 400 天 | `holdings.mark_stale` |
| 两期不可比 | 总值比 < 0.25（差 4 倍） | `holdings._diff` |
| 体检过期 | 30 天 / 漂移 10% | `pmrv` |

### 5.6 显示纪律

- 数字位数：分数 1 位、百分比 2 位、pp 2 位、股数按「股 / 万股 / 亿股」自动换档。
  同一页内不得出现「31.2」与「31.20」混排。
- 金额单位：卫星仓美元（`US$` / `k`）、核心仓人民币（`¥` / 万）、总仓人民币万。
  **换档必须带单位**，`819.7` 后面没有「万」就是错的。
- 「未获取」不显示为 0。缺一个格子比填一个错数好（例：道琼斯估值）。
- 涨跌配色：全项目统一**涨绿跌红**（与 A 股习惯相反）。新增元素一律复用 CSS 变量，
  不硬编码色值。
- 三列等高网格：卡片不足一行就留白，**不改自适应列宽**（会牵动同页其它组的高度对齐）。

### 5.7 去重与聚簇

| 场景 | 规则 | 阈值 |
|---|---|---|
| 新闻源内去重 | 规范化标题前 80 字完全相同 | 精确 |
| 新闻同事件聚簇 | 中文按字二元组、英文按词的 Jaccard 相似度 | ≥ 0.42 |
| 手写稿 vs 原料池 | 同上，手写稿优先 | ≥ 0.42 |
| 新闻 id 冲突 | 手写稿重号时自动改 `x001` 起 | 精确 |
| 专家观点 part 重复 id | 先出现的为准（part 按编号自然排序） | 精确 |
| 13F 证券合并 | (CUSIP, 类别, PUT/CALL) 相同即合并 | 精确 |

**part 排序不能用字符串序**：`sorted()` 里 `part10` 排在 `part2` 前面，
结果是新加的人插到分类中间而不是末尾，「重复 id 以先出现为准」的优先级也跟着错。

## 6. 各页专用算法

### 6.1 新闻分桶（`_hint`）

七个桶不是并列的，是**有序的优先级**——先命中先落桶，避免一条新闻被四个关键词同时抢走：

```
geo（地缘与贸易）→ macro（宏观政策）→ ai（AI 与科技）→ cn（中国国内）→ …→ wire（兜底）
```

- 匹配对象是「标题 + 摘要」的小写拼接。
- 一个关键词都没命中的落 `wire`（快讯流），**不硬塞进别的桶**。
- 分桶建议只是线索，最终由人改。页面显示的是人改过之后的 `place`。

### 6.2 新闻重要性打分（`_score`）

```
时效：≤6h = 4 分，≤24h = 3 分，≤72h = 2 分，更早 = 1 分
同报：+ 2 × (同报家数 − 1)
人工：手写稿 + 2
```

只用于排序，不参与取舍。每一项都能指回原文，所以「为什么这条排第一」可以当场解释清楚。

### 6.3 头条补位（`compose`）

手写头条过期后头条带会整条变成旧闻，所以必须补位：

1. 取手写头条里最新的日期 `newest_top`。
2. 从已上屏的条目中筛出「日期晚于 `newest_top`」的，按时间倒序作为候选。
3. 依次补进头条，直到 8 条上限；被补进来的自动条目从分类流里移除。
4. 排序：先按时间倒序，**再按分数倒序**（两次稳定排序），同分时新的在前。

注意第 4 步的顺序：反过来会让 6 天前的手写头条压在今天的新闻上面。

### 6.4 自动导语（`auto_brief`）

手写导语过期时的兜底，五条，与头条**同源同序**：

1. 取头条带按分数排序的前 5。
2. 不足 5 条时，从六个分类桶里按分数补，**每桶最多一条**。
3. `wire` 不参与补位——它是关键词一个都没命中的长尾（公告、人事、个股回购），
   把它放进「最核心」等于把分类失败当成重要性。
4. 一句话取原文摘要或 `why` 的**首句**，不改写、不压缩。
5. 结果带 `auto: true` 与规则原文 `rule`，页面必须显示。

两边各挑各的会立刻露馅：同一件事在页面上出现两次，标题还不完全一样，读者只会怀疑哪条是真的。

### 6.5 专家观点统计（`stats` / `freshness`）

- 每类：人数、偏多/中性/偏空、要点数、最新要点日期、自动条数、自动最新日期。
- `automatic` 列单独算，**不进多空温度**。
- `freshness`：基准取**运行当天**，不取 `as_of`——用 `as_of` 算永远显示「刚更新过」，
  反而掩盖内容在变旧。差距 > 30 天进 `stale`，无要点进 `empty`。

### 6.6 自动抓取（`windfeed`）

按人名检索 Google News RSS（`when:21d`），落 `data/wind/feed.json`（**不入 git**）。

三条硬口径：

1. **语区按 `org` 判断，不按 `role`。** `role` 是中文写的，按它判会把所有人当中国人。
2. **每人每天只留 1 条。** 按标题相似度合并试过（字符二元组 Jaccard / 包含率），
   同一件事的不同写法得分 0.20~0.58、不同的两件事也能到 0.35，分不开。
   宁可规则笨一点：一天只留最新，五个位置自然落在五天，也不会被一次出访的十篇通稿占满。
3. **标题里出现名字才算命中。** 不命中就丢弃。

**别加「中文简称」别名。** 试过：中文媒体只写姓，「麦克劳德」抓回牙买加 110 米栏选手
和《高地人》里的康纳·麦克劳德。同姓不同人在中文里比拼音更凶。译名只走英文名，
中文转述留给人写。

并发 5 路：再高 Google 会开始返回空。

### 6.7 研报统计

```
n_report      报告数（67）
n_inst        机构数（30）
n_inst_covered 有稿的机构数（30）
n_topic       主题数（5）
n_group       国家分组数（9）
n_cell        有稿的 (机构, 主题) 格子数（62）
n_cell_all    机构 × 主题（150）
```

- 主题内报告按日期倒序，同格最新的在前。
- `n_cell_all` 只用来说明覆盖率的分母，**不是「应该有 150 篇」**。
- 分组按国家，洲内按机构数量从多到少；类型（投行/资管/科技/券商）退到 `kind` 字段，
  只在分组标题后做一行统计。

### 6.8 日历展开

三件事必须分清：

1. **`series`**：一组共用标题/类别/市场的日期（如美国 CPI 的 14 个月度日期）。
   展开成逐条事件，`id` 拼成 `series-YYYYMMDD`。写成 series 的原因：一处改标题全局生效，
   不必担心某一年备注和别年写得不一致。
2. **`repeat`**：目前只支持 `M<日>`（每月第 n 日）。遇周末**顺延到下一个工作日**
   （LPR 的实际做法：2023-05-20 是周六，实际 05-22 公布）。展开项 `id` 拼成 `原id-YYYYMM`。
   法定节假日顺延**不单列**，`note` 里写明「以交易中心公告为准」——与其猜一个挪动日，
   不如让读者自己去看公告。
3. **跨日**：`end` 与 `date` 之间的每一天都要在索引里挂一次（前端展开，`cont` 标记续日），
   否则 CES 这种连开四天的会在月历上只占一格。

排序：`(date, end or date, pri, title)`。

**「当周」有两套算法，必须知道差别**：

| 位置 | 基准 | 结果 |
|---|---|---|
| 后端 `build()["week"]` | `as_of` 所在自然周 | 2026-11-09 ~ 11-15（`as_of` = 11-09） |
| 前端「当周核心事件」 | **浏览器今天**所在自然周 | 本周一 ~ 周日 |

页面用的是前端那套（否则页面打开就是两周前的周），后端 `week` 字段**目前没有任何消费者**。
实现方如果用后端字段，会得到一个过期的「本周」。见 Q2。

### 6.9 13F 聚合

- 只读 `13F-HR` / `13F-HR/A` 的 information table，**不做任何估算**。
- 同一 (CUSIP, 证券类别, PUT/CALL) 的多行合并为一条证券；申报项数另存原始行数（`rows`）。
- **占比分母固定用封面页的 `tableValueTotal`**，不重算、不剔除期权。
- `13F-NT` 是通知不是空仓：跟随 `otherManager.cik` 找到代报主体，把代报主体的申报记在这张卡上，
  并标「代报」。
- 修正申报保留 `amendmentType`，页面标蓝。
- 快照每家只保留前 60 只证券（`TOP_KEEP`），够前 12 + 变化摘要；页面展示前 12（`PAGE_TOP`）。

### 6.10 两期对比（`_diff`）

| 项 | 口径 |
|---|---|
| 增减判定 | **按持股数量**，不按市值（市值是季末价 × 股数，价格涨跌会凭空造出「增持」） |
| 权重分母 | 两期各自的 `tableValueTotal` |
| 期权 | **不进对比**（与详情列表同口径），否则 SPY 的 PUT 会被记成「退出」 |
| 拆股 | 股数成整倍变化且权重变动 ≤ 0.25pp → 标「疑拆股」，**判定仍按申报股数** |
| 不可比 | 两期总值比 < 0.25（差 4 倍）→ 不给逐项，只给倍数与两期规模 |
| 跨期 | `gap_q > 1` 必须写明「中间缺 N 个季度，是累积变动」 |
| 上期是增量修正 | 不当基准，换再上一期 |
| 股数变动 > 10 倍 | 改印两期绝对股数（`148 股 → 695.4 万股`） |

### 6.11 持仓地图汇总

```
只统计 held + add
且 amount 必须是完整「数字k」：^(\d+(\.\d{1,5})?)k$（不区分大小写）
k 固定按 1000 计
watch / option 不计入
纯文字 / put 115 / 2.7k–5 / 裸数字 → 不可计算（既不计入，也不当 0）
未归类（columnId 为空）→ 卡片保留，但不进合计与三种拆分
金额一律用「分」存整数累加（避免 0.1+0.2 在十字相加后显形）
```

一次汇总同时产出三种切法（策略 `g` / 地区 `r` / 主题 `c`）与单元格 `cell`。
**三种切法是同一总额的不同视角，彼此不可相加**——这是这份数据的不变量，
「未归类」不进任何拆分就是为了不让它断掉。

### 6.12 核心仓摊分（`_split`）

```
权重全填 → 按总和归一化（填 40/50/10 与填 4/5/1 等价，不要求凑 100）
部分填  → 没填的按剩余份额等分（0 的意思是「不配这个资产」，与「没填」不同）
全没填  → 按资产个数等分，页面标「等分」
金额切分 → 逐项向下取整，余数补到最大的一份，Σ 恰等于基金金额
```

### 6.13 总仓合并（`total_book`）

```
总仓 = 核心仓（人民币分）+ 卫星仓（美元分 × 7）
三个维度都合并，因为两边语义已对齐：
  国家     ← 卫星仓「地区」+ 核心仓资产「国家」
  风格     ← 卫星仓「策略」+ 核心仓资产「风格」
  资产类别 ← 核心仓资产名 + 卫星仓整体记为「股票」
资产类别里名字带「股票」的一律并进「股票」（cat_key）
```

汇率 7 是整数，所以「美分 × 7 = 人民币分」精确无舍入——这是选 7.00 而不是 7.13 的
附带好处。

### 6.14 体检读数（`pmrvMetrics`）

七个读数的算法见 §4.6.6 的表。三条容易错的：

1. **真防守要按核心仓的「资产名」判，不能看基金名。** 「金和全天候」听着像防守，
   里面 20% 是标普 500、20% 是商品时序 CTA。
2. **卫星仓的黄金按标的名判**（它挂在「贵金属」列下，但性质是商品，不该算进中国 beta）。
3. **地区别名必须合并**：核心 `china/hk` → `cn`，`us` → `us`，`jp/asia` → `asia`。
   不合并的话「中国」只有核心仓那一块，会少掉卫星仓的 6.5 万美元。

一条纪律：**写 JSON 入库文件必须带 `newline="\n"`**。Windows 默认把 `\n` 翻成 `\r\n`，
一次合并就把整篇换行改掉，`git diff` 变几千行全红，真改了哪一行反而看不出来。

### 7.2 写盘纪律（持仓两仓）

```
校验（validate / validate_core）→ 不过就抛，不写
备份（backups/<prefix>-YYYYmmdd-HHMMSS.json，重名加序号，滚动留 30 份）
临时文件（<file>.tmp）→ json.dump(indent=1, ensure_ascii=False) + "\n"
原子替换（os.replace）
返回 {path, bytes, backup, as_of}
```

**顺序不可颠倒**：先备份再写，写坏了能捞；先写再备份，备份的是坏数据。

### 7.3 缓存与内存

- 服务启动时把六页数据装进 `_state`：`wind.build()`、`news.build()`、`load_research()`、
  `holdings.load()`、`portfolio` 由构建期内嵌。
- `GET /api/wind`、`/api/news`、`/api/research`、`/api/holdings` 直接返回内存那份，
  **不做计算**。
- `GET /api/calendar` **每次现算**（读盘 + build），因为它没有「抓取」这一步，
  改完 JSON 刷新页面就该看到。
- `GET /api/portfolio`、`/api/core` **每次读盘**，并各走各的校验；返回「构建之后源文件
  有没有更新过」的对照（`as_of` = 文件 mtime）。
- 改 `data/*.json` 后必须重启服务：缓存不会自己失效。这是本项目最常见的「改了没生效」。

### 7.4 刷新行为矩阵

| 页 | 接口 | 联网 | 耗时 | 重建静态页 | 后台任务 |
|---|---|---|---|---|---|
| 市场新闻 | `POST /api/news/refresh` | 是（17 源） | 10~20s | **是** | 否 |
| 专家观点 | `POST /api/wind/refresh` | 是（127 人） | 40~60s | **是** | 是（轮询） |
| 机构研报 | `POST /api/research/refresh` | 否 | 1~3s | **是** | 否 |
| 财经日历 | 无 | — | — | — | — |
| 大佬持仓 | `POST /api/holdings/refresh` | 是（70 份申报） | 240~300s | 否 | 是（轮询） |
| 当前持仓 | 无（改即写） | 否 | <100ms | 否 | 否 |

**「是否重建」这一列的差异是现状，不是设计。** 大佬持仓不重建的理由是：它只在内存与
localStorage 里更新，页面初次渲染用的是内嵌快照——所以按 F5 会回到构建时那份。
这条列为 Q7。

### 7.5 F5 回退表

| 页 | 点完刷新按 F5 |
|---|---|
| 市场新闻 | 数据仍在（刷新时重建过） |
| 专家观点 | 数据仍在（刷新时重建过） |
| 机构研报 | 数据仍在（刷新时重建过） |
| 财经日历 | 无变化（本来就每次现算） |
| 大佬持仓 | **回到构建时那份**，除非 localStorage 里的快照更新（`built_at` 比较会救回来） |
| 当前持仓 | 数据仍在（写的是源文件，构建期只是内嵌） |

大佬持仓这一条被 localStorage 兜住了，但兜得不彻底：换一台机器、清缓存、换浏览器，
就回到旧快照。这条与温度文档的 Q1 是同一类问题。

### 7.6 性能预算

| 项 | 目标 | 实测（2026-11） |
|---|---|---|
| 六页首屏可交互 | < 1.5s | 单文件 1.6 MB，本地磁盘 |
| 切页 | < 100ms | 纯 `display` 切换，不重渲染 |
| 更新新闻 | < 20s | 10~18s |
| 更新观点 | < 70s | 48~59s |
| 刷新研报 | < 5s | 1~3s |
| 更新持仓 | < 300s | 241~280s |
| 持仓写回 | < 100ms | 单文件 13 KB |

**不要给取数加更短的超时。** 13F 要两份申报 × 35 家，砍超时只会拿到半份。
宁可让用户等 5 分钟看到完整数据，也不要 60 秒给一个残缺快照。

### 7.7 失败与降级

| 场景 | 行为 |
|---|---|
| 新闻抓取全失败 | 沿用上次原料池，按窗口重算，页面照旧；结果条写失败原因 |
| 新闻单个源失败 | 跳过该源，其它照收；源清单里标 `ok:false` |
| 新闻源 200 但内容过旧（>96h） | 整源不收，标「内容过旧」。比 404 更危险，必须逐源查新鲜度 |
| 观点检索某人失败 | 该人无新增，不阻断全局；结果条列「N 位没搜到」 |
| 观点校验失败 | 后台线程 `SystemExit` 单独接住，任务标失败，不静默死掉 |
| 研报校验失败 | 400 拒渲染，带前 5 条错误原文 |
| 13F 某家失败 | `status=error`；若内存里有旧快照，标 `carried` 并沿用 |
| 13F 全部失败 | 保留旧快照，不写占位数字 |
| 持仓写回校验失败 | 400 拒写，页面显示错误，草稿仍在 |
| 持仓写回网络失败 | 徽标转「写回失败 · 草稿还在本机」，给重试按钮 |
| 持仓在 `file://` 下编辑 | 徽标「未连本地服务」，给导出 JSON 按钮 |

**一条通用规则**：任何失败都不清空已有数据。取数失败要显示旧数据 + 一条错误提示，
不是空白页。

## 8. 接口契约

六页共 **15 个接口**：7 个只读、4 个刷新、2 个进度、2 个写回。它们**没有统一的刷新入口**——
这是刻意的：A 股盘中点「更新新闻」时，跑了五分钟的 13F 核对不能被它拖住。

### 8.1 通道总表

| 页 | 读 | 刷新 / 写 | 形状 |
|---|---|---|---|
| 市场新闻 | `GET /api/news` | `POST /api/news/refresh` | 同步，带 `built` |
| 专家观点 | `GET /api/wind` | `POST /api/wind/refresh` + `GET /api/wind/progress` | 后台 + 轮询 |
| 机构研报 | `GET /api/research` | `POST /api/research/refresh` | 同步，带 `built` |
| 财经日历 | `GET /api/calendar` | 无 | 现算 |
| 大佬持仓 | `GET /api/holdings` | `POST /api/holdings/refresh` + `GET /api/holdings/progress` | 后台 + 轮询 |
| 当前持仓 | `GET /api/portfolio`、`GET /api/core` | `POST /api/portfolio`、`POST /api/core` | 读盘 / 写盘 |

统一约定：

- 除两个写接口外，请求体为空。
- 成功 200；校验不过 400；同页正在跑 429；异常 500；锁等待超时 503（只有市场总览用）。
- 所有响应头带 `Cache-Control: no-store, no-cache, must-revalidate`，
  `Content-Type: application/json; charset=utf-8`。

### 8.2 只读接口

```json
GET /api/news        {"ok": true, "news": { ... }}                      // 内存
GET /api/wind        {"ok": true, "wind": { ... }}                      // 内存（含 feed）
GET /api/research    {"ok": true, "research": { ... }, "updated": "2026-11-24 07:02"}
GET /api/holdings    {"ok": true, "snapshot": { ... }}                  // 每次读盘
GET /api/calendar    {"ok": true, "calendar": { ... }, "errors": [], "warnings": []}
GET /api/portfolio   {"ok": true, "matrix": { ... }, "book": "sat",
                      "currency": "USD", "as_of": "2026-11-15 08:54",
                      "error": null, "warn": ["…"]}
GET /api/core        {... 同上，book: "core", currency: "CNY"}
```

四个细节：

1. **`/api/calendar` 的 `ok` 跟的是「校验有没有 error」**，不是请求有没有成功。
   有 error 时 `ok:false` 但仍返回数据（页面可以显示 + 一条警告）。
2. **`/api/holdings` 每次读盘**，不读内存。因为它允许用户在外部改快照文件。
3. **`/api/portfolio` 的 `as_of` 是文件 mtime**，用来判断「构建之后源文件有没有被改过」。
   它与 `matrix.json` 里的任何字段无关。
4. **`/api/wind` 返回的是 `wind.build()` 的结果**，含 `feed`（运行时挂上去的）；
   磁盘上的 `wind.json` **不含 feed**。不要用磁盘文件去校验接口返回。

### 8.3 `POST /api/news/refresh`（同步）

```json
{
  "ok": true,
  "news": { "…完整 news 对象…" },
  "built": true,
  "fetched": {
    "n_pool": 426, "n_items": 100, "n_auto": 100, "n_curated": 0,
    "n_drop": {"curated": 44, "raw": 30, "capped": 296},
    "newest": "2026-11-15T02:32:47+08:00", "days": 7
  },
  "elapsed": 12.4
}
```

- `built`：静态页是否重建成功。失败时仍是 200（数据已经更新），但页面要提示
  「页面重建失败」。
- `fetched` 是给结果条用的，**不是完整数据**。只报总数会让人以为页面该有 248 条。
- 抓取全失败时仍返回 200：沿用旧原料池重算，「抓取失败」写在日志里，
  `fetched.newest` 会是旧值。

### 8.4 `POST /api/wind/refresh`（后台 + 轮询）

第一次调用：

```json
{"ok": true, "started": true, "total": 127}
```

正在跑时再次调用：`429 {"ok": false, "error": "风向正在更新中"}`。

轮询 `GET /api/wind/progress`：

```json
{"ok": true, "running": true, "done": 37, "total": 127,
 "failed": 0, "phase": "检索中", "error": null, "result": null}
```

跑完后（以下为示例值，字段含义见 §4.2.6）：

```json
{"ok": true, "running": false, "done": 127, "total": 127, "failed": 0,
 "phase": "完成", "error": null,
 "result": {
   "wind": { "…完整 wind 对象…" },
   "built": true,
   "build_ms": 2180,
   "diff": {
     "people": 0, "points": 0, "feed": 3, "n_feed": 506, "n_feed_people": 117,
     "feed_fetched_at": "2026-11-24 07:31", "feed_latest": "2026-11-23",
     "latest": "2026-11-22", "latest_before": "2026-11-22",
     "dropped": ["…"],
     "new": 3, "added_by": {"macleod": 3},
     "added_names": [{"cn": "麦克劳德", "n": 3}],
     "hit_people": 116, "items": 503, "total": 127,
     "nofeed": [{"id": "…", "cn": "…"}]
   },
   "elapsed": 52.7
 }}
```

- `phase` 会在 `检索中` → `合并与重建` → `完成 / 失败` 之间变。
- **`result` 只在跑完时带**，跑的过程中是 `null`（不反复传 200 KB）。
- `build_ms` 成功是整数毫秒，**失败是错误文本**。这是类型不稳定，见 Q6。
- 校验失败走 `SystemExit`，要单独接住写进 `error`，否则线程静默死掉。

### 8.5 `POST /api/research/refresh`（同步）

```json
{"ok": true, "research": { ... }, "updated": "2026-11-24 07:02",
 "built": true, "build_ms": 1904, "elapsed": 2.1}
```

校验不过：

```json
{"ok": false, "error": "数据校验未通过：研报数据校验失败：…（前 5 条）"}
```

HTTP 状态是 **400**，不是 500。区分这两者的意义：400 是「你给的文件有问题」，
500 是「我的代码坏了」。

### 8.6 `POST /api/holdings/refresh`（后台 + 轮询）

```json
{"ok": true, "started": true, "total": 35}
```

正在跑：`429 {"ok": false, "error": "持仓正在核对中"}`。

`GET /api/holdings/progress`：

```json
{"ok": true, "running": false, "done": 35, "total": 35, "failed": 0,
 "error": null, "snapshot": { "…完整快照…" }}
```

- `snapshot` 只在跑完时带（不反复传 380 KB）。
- 跑完后前端要做「carried 合并」：本次失败但有旧数据的机构，用旧数据填回，
  `status` 改成 `carried`（不是 `error`），并保留原始失败原因到 `keep_error`。

### 8.7 写接口（持仓两仓）

```
POST /api/portfolio   {"matrix": { …完整卫星仓对象… }}
POST /api/core        {"matrix": { …完整核心仓对象… }}
```

成功：

```json
{"ok": true, "sum": { …汇总… }, "book": "sat",
 "path": "data/portfolio/matrix.json", "bytes": 13602,
 "backup": "matrix-20261124-070233.json", "as_of": "2026-11-24 07:02"}
```

失败：

| 状态 | 场景 | 响应 |
|---|---|---|
| 400 | 请求体不是合法 JSON | `{"ok": false, "error": "请求体不是合法 JSON"}` |
| 400 | 校验不过 | `{"ok": false, "error": "数据校验失败：…（前 3 条）"}` |
| 500 | 写盘异常 | `{"ok": false, "error": "<异常文本>"}` |

**写接口是全项目唯一会改源文件的地方。** 三条硬要求：

1. 校验不过**不写半份**。
2. 写前必须备份，备份文件名回给前端（用户要知道去哪儿捞）。
3. 串行化（`_pm_lock`），两次保存不能交错。

### 8.8 错误码与前端行为

| HTTP | 场景 | 前端行为 |
|---|---|---|
| 200 `ok:true` | 正常 | 重渲染，按钮恢复，结果条写结果 |
| 200 `ok:false` | 日历 / 持仓读接口的「有 error 但有数据」 | 显示数据 + 一条警告，不能当失败处理 |
| 400 | JSON 或校验失败 | 按钮恢复，把错误原文前 60 字显示出来；**保留页面上已有数据** |
| 429 | 同页正在跑 | 按钮立即恢复可点，提示「正在更新中，稍后再试」；**不得进入 loading 死等** |
| 500 | 取数 / 写盘异常 | 按钮恢复，显示原文；旧数据不清空 |
| 网络中断 | 服务没起 / `file://` | 提示「连不上本地服务」+ 重启命令；持仓页转「只在本机」模式 |

### 8.9 锁清单

| 锁 | 保护 | 粒度 |
|---|---|---|
| `_news_lock` | 新闻刷新 | 每页一把 |
| `_wind_lock` | 观点检索 + 进度读写 | 每页一把（进度与任务共用） |
| `_hld_lock` | 13F 核对 + 进度读写 | 每页一把 |
| `_res_lock` | 研报重读 + 重建 | 每页一把 |
| `_pm_lock` | 两个仓的写回 | 两仓共用一把（都是小文件，串行代价可忽略） |

刷新类用 `acquire(blocking=False)`，抢不到直接 429，**不排队**。
理由：这些操作在 10~300 秒量级，排队会让用户以为点第二下没反应。

**不允许改成一把全局锁**：那会让 A 股盘中的新闻刷新把五分钟的 13F 核对一起堵住。

## 9. 数据结构

字段名是实现契约，改字段名等于改接口。所有文件 UTF-8、`ensure_ascii=False`。

### 9.1 `data/news/news.json`

| 字段 | 类型 | 说明 |
|---|---|---|
| `as_of` | str | 合成日期 `YYYY-MM-DD` |
| `window` | obj | `{top: [起, 止], flow: [起, 止], days: 7}`，ISO 带时区 |
| `brief` | obj/null | 导语 `{title, items: [{h, t, src?, date?, bucket?}], auto?, rule?, as_of?}` |
| `buckets` | arr | 七个桶的 `{id, name, desc, rule}`，顺序固定 |
| `items` | arr | 上屏条目，见下 |
| `n_items` / `n_top` / `n_auto` / `n_curated` | int | 计数 |
| `n_drop` | obj | `{curated, raw, capped}` |
| `raw` | obj | `{fetched_at, n_pool}` |
| `stats` | arr | 按桶统计 `[{id, name, n, latest}]` |
| `fresh` | obj | `{ref, newest, age_h, n}`，基准是运行时刻 |

`items[]`：

```json
{"id": "a003", "auto": true, "place": "top", "t": "标题", "tcn": "90 字摘要",
 "src": "BBC", "date": "2026-11-15T02:28:06+08:00", "url": "https://…",
 "n_src": 2, "lang": "en", "rank": 1}
```

人写条目（`auto` 缺省）额外要求 `why`（≤60 字）与 `impact`（股/债/汇/商品/加密 的任意子集），
且**不得带 `auto`**。`carry: true` 只允许出现在 `place == "top"` 且最多 2 条。

### 9.2 `data/wind/wind.json` 与 `feed.json`

| 字段 | 类型 | 说明 |
|---|---|---|
| `as_of` / `updated` | str | 快照日、人工更新时刻 |
| `window` | [str, str] | `["2026-08-01", "2026-11-16"]`，**是策展覆盖范围，不是冻结线** |
| `brief` | obj | `{title, items: [{h, t}], dropped: [标题]}` |
| `cats` | arr | 六类 `{id, name, desc, groups?: [{id, name}]}` |
| `people` | arr | 人物，见下 |
| `stats` | arr | 每类 `{id, name, bull, neutral, bear, n, points, latest, auto, auto_latest}` |
| `n_people` / `n_points` / `n_feed` / `n_feed_people` | int | 计数 |
| `latest_point` | str | 最新一条**人写**要点的日期 |
| `fresh` | obj | `{ref, days: 30, stale: [...], empty: [...], ok}` |
| `feed_fetched_at` / `feed_days` | str / int | 自动抓取时刻与窗口（21 天） |

`people[]`：

```json
{"id": "druckenmiller", "name": "Stanley Druckenmiller", "cn": "德鲁肯米勒",
 "role": "Duquesne 家族办公室创始人", "org": "Duquesne Family Office",
 "cat": "macro", "grp": "buy", "tag": "bear",
 "stance": "看空 AI 估值与长债…",
 "points": [{"date": "2026-10-29", "src": "X 帖（@standuquesne）", "text": "…"}],
 "feed": [{"date": "2026-11-10", "src": "NewsNation", "title": "…", "url": "…"}],
 "feed_date": "2026-11-14"}
```

`cat` ∈ `macro / value / tech_investor / tech_leader / central_bank / gov`；
`tag` ∈ `bull / neutral / bear`；`points` ≤ 5 条（超过告警）；`feed` ≤ 5 条。

**`feed` 不是 `points`**：前者机器搬、每次刷新覆盖，后者人写、永不因抓取而减少。
两者不能合并存储（§5.3）。

### 9.3 `data/research/research.json`

| 字段 | 类型 | 说明 |
|---|---|---|
| `as_of` / `window` | str / [str,str] | 快照日、报告窗口 |
| `topics` | arr | 五个主题 `{id, name, desc, note?}` |
| `insts` | arr | 机构 `{id, cn, en, grp, kind, focus}` |
| `reports` | arr | 报告，见下 |

`reports[]`：

```json
{"id": "gs_macro_us", "inst": "gs", "topic": "macro", "scope": "美国",
 "date": "2026-10-30", "title": "盈利加速期结束，但还不是熊市",
```

- `grp` ∈ `us / ca / uk / fr / de / ch / es / jp / cn`，**同一国家的机构必须相邻**（校验会报错）。
- `kind` ∈ `投行 / 资管 / 科技 / 券商`（不在集合内只告警）。
- `thesis` 与 `pts` 是判断，只能人写。

### 9.4 `data/calendar/calendar.json`

| 字段 | 类型 | 说明 |
|---|---|---|
| `as_of` | str | 数据截至（**不是今天**） |
| `range` | [str, str] | 覆盖范围，当前 `2026-11-01 ~ 2027-12-31` |
| `updated` | str | 人工更新时间 |
| `events` | arr | 单条事件 |
| `series` | arr | 共用标题的多日期组 |

`events[]`：

```json
{"id": "ciie-2026", "date": "2026-11-05", "end": "2026-11-10",
 "type": "conf", "mkt": "cn", "title": "中国国际进口博览会",
 "pri": 2, "sub": "第九届，上海", "conf": "estimated",
```

- `type` ∈ 7 类：`earnings / conf / launch / cb / data / pol / summit`。
- `mkt` ∈ 8 个：`us / cn / hk / tw / jp / kr / eu / global`。
- `conf` ∈ `confirmed / estimated / tbd`；`estimated` **必须带 `note`**。
- `pri` 1~3（1 最重要）。
- `repeat` 只有 `M<日>` 一种形式；`end` 最多跨 14 天（超了告警）。
- `series[]`：`{id, title, type, mkt, pri?, conf, src, note?, dates: [日期…]}`。

`build()` 的输出（页面消费的那份）多出 `types`、`mkts`、`week`、`stats`：


## 10. 非功能要求

### 10.1 性能

见 §7.6。三条补充：

- **首屏不发起任何数据请求**：六页数据全部构建期内嵌，进页面即可读。
  只有用户点刷新、或进当前持仓需要对照源文件时，才发请求。
- **刷新期间界面不假死**：按钮 `disabled` + 文案变化 + 进度数字，三样至少两样。
- **13F 核对是五分钟级操作**，必须有进度（`done/total`），不能只转一个圈。

### 10.2 体积

| 项 | 当前 | 说明 |
|---|---|---|
| 单文件 HTML | **1.65 MB** | 含六页数据与全部样式脚本 |
| `wind` 内嵌 | 294.6 KB | 127 人 / 458 条要点 + 503 条自动标题（自动块占了约 230 KB） |
| `holdings` 内嵌 | 134.5 KB | 每家只留前 12 项；全量 254 KB |
| `calendar` 内嵌 | 68.9 KB | 377 条（展开后） |
| `news` 内嵌 | 37.3 KB | 100 条 |
| `research` 内嵌 | 34.5 KB | 67 篇 |
| `portfolio` 内嵌 | 19.5 KB | 卫星 10.8 + 核心 4.9 + 体检 3.8 |

**不要为了瘦身把数据改成运行时拉取。** 首屏依赖构建期快照是这个看板的核心设计
（双击 HTML 就能看），改成异步会让 `file://` 直接不可用。

### 10.3 可视化

- 六页共用一套色板与卡片样式，不各自引入新配色。
- 涨跌配色：**涨绿跌红**，复用 `--up` / `--dn`。
- 立场三色：偏多 / 中性 / 偏空，在六页里含义一致（专家观点的人物、研报的标签、
  新闻的影响面都用同一套语义映射）。
- 三列等高网格：不足一行留白，不改自适应列宽。
- 覆盖矩阵的空格用「·」而不是空白，让「这里看过、确实没有」可分辨。

### 10.4 可访问性

- 六个页签、两个分组按钮都是真实 `<button>`，支持 Tab 与 Enter。
- 立场、确认度、状态徽标不能只靠颜色：必须同时有文字（「偏多」「推测」「修正」）。
- 数字与单位之间不加空格（`31.2%`、`819.7 万` 的中文排版按项目既有规则）。
- `title` 属性只做补充，不能承载唯一信息（移动端没有悬停）。

### 10.5 健壮性

- 任一数据文件缺失 → 该页显示「数据文件不存在」，其余五页正常。
- 任一校验失败 → 该页拒渲染并显示错误（研报 / 日历是硬拒；新闻与观点只告警）。
- 服务重启后 → 六页都能从落盘文件恢复，不需要重新抓取。
- 持仓写盘失败 → 草稿仍在，页面不丢内容（§4.6.5）。
- `file://` 打开 → 六页都能看，五页只读，持仓页可编辑但明确提示「只在本机」。

### 10.6 离线

- 不依赖任何 CDN：样式、脚本、字体、图标全部内联。
- 断网时页面完整可读，只有刷新按钮会失败（并给出原因）。

## 11. 验收标准

每条都能用「打开页面看一眼」或「点一次按钮」判定，不写「体验良好」这类无法验收的话。

### 11.1 结构与导航

| 编号 | 验收项 | 判定方法 |
|---|---|---|
| AC-1 | 第一层有「观点」「持仓」两组；观点含 4 页、持仓含 2 页 | 数按钮 |
| AC-2 | 六个 hash 都能直达：`#news` `#wind` `#research` `#calendar` `#holdings` `#portfolio` | 地址栏逐个改 |
| AC-3 | 切组后回到该组上次停留的页，而不是组内第一页 | 观点→机构研报→切持仓→切回观点 |
| AC-4 | 点页签回写地址栏，且**不增加浏览器历史条目** | 连点三次，后退应直接离开看板 |
| AC-5 | 认不出的 hash 落在市场总览 | 输 `#foo` |
| AC-6 | 1280 宽下页签栏无横向溢出 | 量 `scrollWidth <= clientWidth` |

### 11.2 数据正确性

| 编号 | 验收项 | 判定方法 |
|---|---|---|
| AC-7 | 新闻七个桶条数之和 + 头条数 = `n_items` | 相加（12+12+11+11+12+0+34+8 = 100） |
| AC-8 | 新闻 `n_auto + n_curated = n_items` | 100 + 0 = 100 |
| AC-9 | 空桶显示「窗口内无重大事项——不凑数」，不隐藏 | 看「传统产业」 |
| AC-10 | 手写导语过期（>48h）时不显示，且出现「自动摘要」标识块 | 改 `as_of` 到 3 天前重算 |
| AC-11 | 专家观点六类人数之和 = `n_people` | 27+9+16+34+10+31 = 127 |
| AC-12 | 每类多/中/空之和 = 该类人数 | 抽查政府：2+24+5 = 31 人；全库 58+48+21 = 127 |
| AC-13 | 本期主线最多 10 条，超出部分在悬停里列出标题 | 数条数 + 悬停 |
| AC-14 | 自动抓取块里没有多空标签、没有「认为」类转述 | 逐条看 |

## 12. 已知边界与待确认问题

标注 **【现状】** 的是发现了但本轮不改的，**【必须定】** 的是实现方动工前必须给答复的。

### Q1【必须定】新闻页 100 条全部「未策展」，页面上没有一个「为什么重要」

页面内嵌的是**构建时现算**的数据：`as_of = 2026-11-24`、`n_items = 100`、
`n_top = 8`、**`n_curated = 0`**、`n_auto = 100`、`brief.auto = true`。

也就是说：

- **头条区 8 条全部标「未策展」**，分类流 92 条也全部标「未策展」。
- 导语是自动摘要（取头条前五，原文首句），不是人写的判断。
- 页面上**没有任何一条 `why`**（为什么重要）——而这个页面存在的理由就是那句话。

这不是算法错，是**内容没跟上**：`issue*.json` 只有 `issue1.json` 一份，里面 44 条
全部过期（`n_drop.curated = 44`），所以策展层一条都没进来。

**还有一个更容易踩的陷阱**：磁盘上的 `data/news/news.json` 是 **11-15** 的旧版，
与页面里的 11-24 不一致。原因是构建会现算并重写这个文件，而本项目的收尾流程会在提交前
把它 `git checkout` 还原（它是运行态噪音）。所以：

> **不要拿 `data/news/news.json` 去校验页面。** 页面数据是 `news.build()` 的返回值，
> 磁盘文件可能已经被还原成上一版。要校验就跑一次 `compose(save=False)`。

用户已明确这块滞后处理，本轮不动内容。但文档要记两条：

1. **通用过期条**：`generated` / `as_of` 距运行日超过 3 个自然日，页首显示黄色过期条。
   现在只有新闻页有按小时算的陈旧条（>12 小时），其余五页没有。
2. **「未策展」不能变成常态**：当 `n_curated / n_items < 10%` 时，页首应显示一行
   「本期没有人工策展，以下全部是原料池搬运」。100% 未策展时更要说清楚——
   否则读者会把机器搬的标题当成编辑选过的内容。

### Q2【必须定】财经日历的「当周」有两套算法

- 后端 `build()["week"]` 以 `as_of`（2026-11-09）所在自然周为基准 → `11-09 ~ 11-15`。
- 前端「当周核心事件」以浏览器今天为基准 → 本周一 ~ 周日。

页面用的是前端那套，后端的 `week` 字段**没有任何消费者**。这本身没问题，
但它是一颗雷：实现方看到接口里有 `week` 就会用，用了就得到两周前的「本周」。

**需要答复**：删掉后端 `week`（推荐），或改成「以请求时刻为准」并在文档里写清。
不要留一个语义过期、没人用、但看起来很像能用的字段。

### Q3【现状】日历的 `as_of` 停在 11-09

`calendar.json` 的 `as_of` 与 `updated` 都是 2026-11-09，截至今天 15 天。
它是前瞻到 2027-12-31 的日程表，所以「15 天没更新」不像新闻那样致命——
11-10 之后新增的临时会议、改期的数据发布不在里面。

**处理**：页脚显示「数据截至 2026-11-09」就够（已有）。但**不要**在这页放刷新按钮：
它抓不到东西，放一个按钮只会让人以为「点了就能拿到最新公告」。

### Q4【现状】13F 有 18 家在 Q2、15 家在 Q3

`periods` 分布：`2026-06-30` 18 家、`2026-09-30` 15 家、`2025-09-30` 1 家（Scion）、
`2023-09-30` 1 家（Chanos）。所以：

- 页面**不能显示「最新季度」**，否则读者以为 35 家都交了 Q3。
  现在的口径是「家数最多的那个季度 + 另有 N 个季度」，这是对的。
- 「季度变化」里每家比的是**它自己**的相邻两期，所以 35 家的对比窗口不是同一天。
  这一条要看详情里的 `2026Q1 → 2026Q2` 才看得出来。

**需要确认**：这一组是否需要「统一到同一季度再比」的视图？我的判断是不需要——
13F 的披露节奏本来就不齐，统一反而会丢掉一半机构。但实现方必须让「每家比的是哪两期」
在卡片上可见，不能让读者以为这是同期横比。

### Q5【现状】持仓页的 localStorage 快照优先

`hInitHoldings()` 会读 `hld_snap_v1`，与内嵌快照按 `built_at` 比新旧，取新的那个。
好处：刷新后不回退、同一天抓两次也能拿到新的。代价：

- 换浏览器 / 清缓存 / 换机器 → 回到构建时那份（可能是几天前）。
- 两个标签页同时开着，后刷新的一方会覆盖 localStorage，另一个标签页看到的还是旧数据。

**处理**：保留现状（它解决了更痛的问题），但要在页面某处能看出「这份快照来自本机缓存」。
最简单的做法：详情页的「快照 2026-11-16」后面，若来自 localStorage 就标「（本机）」。

### Q6【必须定】`build_ms` 成功是数字、失败是字符串

`/api/wind/refresh` 的 `result.build_ms` 与 `/api/research/refresh` 的 `build_ms`：
成功是整数毫秒，失败是错误文本。前端若按数字解析会显示 `NaN` 或抛错。

这条与温度文档的 Q10 是同一条，**建议一起改**：拆成 `build_ms: int|null` 与
`build_error: str|null`。若维持现状，前端必须显式判类型。

### Q7【现状】大佬持仓刷新后不重建静态页

新闻、观点、研报刷完都会跑 `rebuild_dashboard.py`；大佬持仓**不跑**。
它只更新内存与 localStorage，所以：

- 同一台机器：localStorage 兜住了，F5 不回退。
- 换浏览器：回到构建时那份。

**为什么当初没统一**：13F 要抓 70 份申报（五分钟），再花 2 秒重建页面，边际成本很低。
真正的顾虑是「重建页面会重写 1.6 MB 文件，而这次只改了持仓一块」。但这个理由不足以
支撑一个会让用户在换设备后看到旧数据的差异。

**建议**：统一重建。与温度文档 Q1 一并决策，否则项目里会存在三种 F5 行为。

### Q8【现状】`wind.json` 里主线有 11 条，上限是 10

磁盘上是 11 条，`_finalize()` 在运行时截到 10 并把第 11 条标题放进 `dropped`。
所以**磁盘与页面不一致**：用 `wind.json` 校验页面会以为少了一条。

**处理**：保留（截断发生在出口，数据不丢），但实现方必须知道：`wind.json` 是**原料**，
不是**页面数据**。页面数据要过 `_finalize()`。

### Q9【现状】研报覆盖 62/150 格，空格是信息还是缺口

30 家 × 5 主题 = 150 格，有稿 62 格。空白格 88 个。两种解读：

- 「这家没覆盖这个主题」——是信息（它的能力圈就在那一块）。
- 「我们还没收到这篇」——是缺口（该补）。

页面上分不出来，因为数据里没有「无稿」这个状态，只有「没这条记录」。

**需要答复**：要不要引入 `coverage: none` 的显式状态（人确认过「这家确实不写这个」）？
不引入的话，覆盖矩阵的空格只能读作「本期无稿」，不能读作「不看这个」。
现在页面的文案是「本期无稿」，这是诚实的下限。

### Q10【现状】汇率固定 7.00

总仓、体检、所有历史对比都用 7.00。即期汇率只在体检卡里做一次对照，不参与合计。

- 好处：历史可比。汇率一动就改合计，月度对比立刻失效。
- 代价：记账口径与「今天能换回多少」会差一截。11-15 那份判断里记的是
  卫星仓 289.7 万 → 即期 276.0 万，差 13.6 万（约 1.7% 总仓）。

**处理**：保持固定。但体检卡的对照必须一直显示，且写明「即期只作对照，不进合计」。
不要为了「更准」把 `FX` 改成实时价——那会让所有历史读数失去可比性。
